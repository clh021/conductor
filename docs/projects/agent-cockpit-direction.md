## 文档目的

本文档用于整理当前阶段对产品方向的判断，供进一步评估。

本文档的目标不是进入实现细节，而是先确认以下问题：

- 这个产品真正要解决的核心问题是什么

## 核心问题

当前真实需求，不是下面这些任意一种单独成立的东西：

- 一个工作流编排器
- 一个新的 AI Coding Agent
- 一条代码审查流水线
- 一个简单的聊天界面

当前真实需求是一个能够围绕现有 AI Coding Agent 持续进行监督、纠偏和协作的系统。

这个系统需要同时满足以下要求：

- 保留 `codex`、`reasonix`、`opencode` 等现有工具本身的能力
- 能稳定读取并展示这些工具输出的非代码内容
- 允许用户在执行过程中随时介入
- 支持用户纠偏、改方向、补约束、补场景
- 支持连续协作，而不是仅在固定节点审批
- 后续可以扩展到编排、评审、回放、审计和自动化

因此，目标产品不应被定义为普通工作流系统，而应被定义为一个面向 AI Coding Agent 的监督与协作系统。

## 产品本质定义

当前最准确的产品定义，已经不应只停留在“驾驶舱”这个层面。

更完整的定义应当是：

**一个以需求记忆为核心、以会话监督为交互表层、以持续纠偏和可重评估为目标的 Agent 协作平台。**

其中：

- “需求记忆”是内核
- “监督驾驶舱”是主要交互表层
- “持续纠偏”是运行时能力
- “可重评估、可重构、可重新推进”是长期结构目标

这一定义包含四个关键点：

### 1. 以会话为中心

系统的核心对象不是单个步骤，而是一次连续执行和连续协作的会话。

### 2. 以需求为锚点

系统判断是否正确、是否完成、质量是否达标，不能只看代码结果，必须始终回到用户最初的真实需求。

### 3. 以纠偏为核心能力

系统最重要的能力不是“自动完成”，而是“允许人在过程中持续修正方向”。

### 4. 以现有 Agent 为执行主体

系统不应优先重造 `codex`、`reasonix`、`opencode` 本身，而应优先成为这些工具之上的监督层和协作层。

### 5. 以“可脱离历史负担重新评估”为结构目标

系统必须允许用户在任意阶段做下面这些事情，而不必被“已经推进到一半的历史实现”绑死：

- 抽出原始需求和高优先级记忆重新评估
- 判断当前方向是否已经偏离
- 在不背历史技术包袱的情况下重新推进
- 必要时做彻底重构

因此，这个平台不能只是一层实时交互壳，它还必须是一个可靠的需求、约束、决策与场景记忆系统。

## 为什么 Conductor 不是核心产品形态

`conductor` 有价值，但它不是当前产品的核心形态。

`conductor` 的强项是：

- 工作流编排
- 路由与分支
- checkpoint 与 resume
- human gate
- 节点级 dialog
- 多步骤执行管理

这些能力后续可能很有帮助，但它们解决的是“流程控制”问题，不是“连续监督和纠偏”问题。

当前最优先解决的问题是：

- 如何持续保存用户真实需求
- 如何在执行过程中判断是否偏离
- 如何允许用户在过程中随时修正
- 如何保留 agent 输出、用户输入和后续判断之间的对应关系
- 如何在未来某个时点，把最重要的一批原始记忆直接抽取出来做重新评估

因此，当前判断是：

- `conductor` 可以成为后续的外层流程编排组件
- `conductor` 不适合作为核心交互壳
- 第一阶段产品不应围绕 YAML workflow 展开

## 首选交互模型

当前最合理的交互模型是：

- `Web` 为主交互界面
- 必要时保留 `TUI` 作为补充
- 原生 Agent 继续作为执行主体
- 系统负责监督、展示、记忆、纠偏、评估和记录

这个交互模型明确排除以下方向作为第一优先级：

- 把所有能力强行压缩成命令行脚本调用
- 把全部能力建立在 YAML workflow 之上
- 为了统一而牺牲原有 agent 的自然交互能力

## 为什么 Web 更适合作为主界面

将纠偏和监督会话放到 `Web` 界面中，更符合目标能力。

`Web` 的主要优势包括：

- 更适合展示长文本输出
- 更适合同时展示需求、上下文、diff、文件和操作区
- 更适合保留完整会话记录
- 更适合提供暂停、继续、回放、分叉等操作
- 更适合作为“监督驾驶舱”而不是单纯聊天框

但需要明确：

`Web` 只会降低交互层的难度，不会自动解决底层 agent 接入问题。

即使使用 `Web`，仍然必须解决以下问题：

- 如何接入不同 agent 的会话
- 如何中断与继续
- 如何统一会话转录记录
- 如何记录 workspace 变化
- 如何把用户纠偏反馈送回原有 agent

因此，`Web` 是正确的主交互表层，但不是全部问题的答案。

## 浏览器插件不是第一阶段基础方案

浏览器插件可以作为后续增强方式，但不适合作为第一阶段基础架构。

原因如下：

- 对第三方页面结构依赖过强
- 稳定性较差
- 很难成为权威数据源
- 难以稳定控制本地 CLI/TUI 会话
- 更适合做外挂，不适合做主系统

因此，当前更合理的基础方向是：

- 先做一个独立的 `Web` 驾驶舱
- 后续如果有必要，再考虑浏览器插件作为附加层

## 当前接近的市场方向

目前市面上存在一些相近方向的项目，但没有看到一个完全满足当前需求、并且能直接作为现成答案的成熟产品。

### OpenCode

`OpenCode` 当前看起来最接近一个适合作为实验底座的对象。

原因是它同时具备：

- Web 使用方式
- TUI 使用方式
- attach / session 类能力
- server / plugin 扩展能力

这使它更容易成为“监督层”的第一接入对象。

### Reasonix

`Reasonix` 更偏向终端使用和 agent 本体能力。

它仍然值得纳入目标接入范围，但它看起来不像一个天然适合作为监督驾驶舱底座的系统。

### Codex

`Codex` 本身能力强，但它有自己的原生生态和交互方式。

如果过早把它强行降级成脚本子进程，可能会损失它本身的优势。

因此，针对 `Codex` 更适合做“受保护的原生接入”，而不是“简单脚本调用”。

### OpenHands

`OpenHands` 更接近通用型 Web Agent 平台或控制平面。

它是一个重要参考对象，但它偏重平台化，不一定正好匹配当前这个更聚焦的监督驾驶舱目标。

## 当前方向判断

截至目前，最合理的方向判断是：

**要做的不是工作流系统，而是一个以需求记忆和持续纠偏为核心的 Agent 监督驾驶舱。**

这意味着系统的核心对象应当是：

- 需求
- 会话
- 会话转录记录
- 用户纠偏
- 决策记录
- workspace 状态
- 偏离与完成度评估
- 可抽取、可迁移、可重评估的高优先级记忆集合

而不是只围绕：

- prompt
- 单次执行
- 脚本输出
- 节点路由

## 最高优先级原则

当前最高优先级，不是技术选型，不是架构风格，也不是二次开发方式。

当前最高优先级是：

**准确保存、解释、追踪和评估用户真实需求，尤其是与使用场景直接相关的部分。**

这是整个系统的第一原则。

因为它直接决定：

- 项目是否偏离
- 项目是否完成
- 输出质量是否达标
- 未来是否可以脱离既有历史负担，重新判断方向是否仍然成立

只有在这个前提成立后，下面这些内容才有意义：

- 技术偏好
- 架构选择
- 工具选择
- 二次开发策略
- 接入方式

## 必须把用户输入提升为一等数据

用户输入不能只被当作聊天消息保存。

系统必须把用户输入当作一等数据处理，尤其是以下类型：

- 原始需求
- 场景补充
- 约束说明
- 纠偏说明
- 拒绝说明
- 完成判断
- 质量判断
- 技术偏好
- 技术架构判断
- 技术选型决策
- 重构理由
- 放弃某条方案的理由

这意味着系统必须具备一个专门的“需求记忆层”。

## 需求记忆层是核心系统，而不是附属功能

这个系统不应只被看作：

- Agent 执行层

它应被看作：

- 需求记忆层
- 加上 Agent 执行层

需求记忆层负责提供：

- 方向判断依据
- 偏离判断依据
- 完成判断依据
- 质量判断依据
- 变更追踪依据
- 审计与回放依据
- 脱离当前实现重新评估的依据
- 从旧路径快速切换到新路径的依据

如果没有这一层，系统最多只是一个更好看的 Agent 聊天壳，而不是一个真正可靠的监督系统。

## 需求记忆必须有优先级分层

所有输入和记忆不能被视为同等重要。

当前建议的优先级分层如下。

### P0：任务本质层

用于保存最根本、最不可丢失的信息，包括：

- 原始需求
- 使用场景
- 用户目标
- 成功定义
- 非目标
- 边界条件

这是最高优先级层。

后续所有判断，必须首先服从这一层。

### P1：纠偏约束层

用于保存后续出现的高优先级修正，包括：

- 明确纠偏
- 防偏离约束
- 禁止事项
- 优先级变化

这一层用于修正执行方向，但不能静默抹掉 P0 原始基线。

### P2：方案偏好层

用于保存方案层面的倾向，包括：

- 技术偏好
- 架构偏好
- 工具选择偏好
- 交互偏好

这一层重要，但它不能凌驾于 P0 和 P1 之上。

### P3：实现细节层

用于保存局部实现层面的内容，包括：

- 命名建议
- refactor 想法
- 局部实现偏好
- 次级工程决策

这一层只应影响实现细节，不应反向改变任务本质。

这里的“权重”可以理解为记忆对后续判断的约束强度，P0 和 P1 本身就属于高权重内容，正式落档时应优先人工确认；P2 和 P3 可以更宽松，但也不能悄悄覆盖高权重内容。

## 原始需求必须永久保留

原始需求绝不能被系统摘要替代。

原始需求应被作为基线永久保留，并具备以下属性：

- 原文不可丢失
- 原文不可被自动总结覆盖
- 后续可以补充，但不能静默改写
- 所有后续判断都可以追溯回原文

如果存在冲突，默认规则应当是：

- 原始需求原文优先
- 除非存在明确、可追踪的后续修正

这条规则还有一个更重要的长期价值：

当未来发现当前路线不适合时，系统仍然可以立即提取出最高优先级的原始记忆，用它们重新开始评估，而不是只能沿着旧路线继续修补。

这正是需求记忆系统和普通聊天记录系统之间最重要的区别之一。

## 需求增量必须被单独记录

后续每一次纠偏、澄清、补约束，都不应只是简单追加一句消息。

这些内容应被视为“需求增量”。

需求增量应当明确指出它在修改什么，例如：

- 目标
- 场景
- 范围
- 质量标准
- 约束
- 非目标
- 技术偏好

只有这样，系统才能回答以下关键问题：

- 现在的任务要求到底是什么
- 哪些内容是后加的
- 哪些内容取代了旧约束
- 当前执行依据的到底是哪一版要求
- 如果当前路线被判定为错误，应该回退到哪一层要求重新开始

## 必须支持“高优先级记忆脱钩重评估”

当前需要明确加入一个重要未来场景：

系统中的高优先级记忆，不应被当前实现路径绑定。

换句话说，系统必须支持在任意阶段把下面这部分内容单独抽出来重新审视：

- 原始需求
- 场景需求
- 用户目标
- 成功标准
- 非目标
- 高优先级纠偏约束
- 架构层关键决策
- 技术选型决策及其理由

这部分信息应具备以下特征：

- 独立成体系
- 可归档
- 可版本化
- 可重新组合
- 可在不继承旧实现负担的前提下重新进入评估流程

因此，这个平台的定位必须从“监督驾驶舱”扩展为：

**需求记忆系统 + 会话监督驾驶舱 + 可重评估决策档案层**

## 必须具备分类、标签和归档能力

需求记忆系统需要分类、标签和归档功能。

这不是为了做一个“更方便搜索的笔记系统”，而是为了给后续判断提供稳定结构。

分类和标签至少要支持以下维度：

- 场景
- 目标
- 约束
- 质量要求
- 架构倾向
- 工具倾向
- 风险
- 状态
- 决策
- 决策理由
- 放弃理由
- 可回退锚点

当前建议方向是：

- 核心标签使用受控分类
- 允许附加自由标签
- 评估逻辑优先依赖受控分类

归档能力的意义不仅是“保留历史”，更是“允许在未来快速重新起盘”。

也就是说，归档不是被动备份，而是主动支持下面这些能力：

- 重新评估
- 重新规划
- 局部推翻
- 全量重构
- 平行方案对比

## 记忆存储形态的方向判断

基于已有经验，当前应当明确一个重要判断：

**版本化的 `Markdown` 记忆文档必须作为唯一真相源，数据库只应作为增强读写与检索层存在。**

这条判断非常重要，因为它直接关系到需求记忆系统未来是否可重评估、可迁移、可审计、可脱离当前实现继续存活。

### 为什么 `Markdown` 必须是唯一真相源

如果需求记忆、纠偏记录、关键决策、场景约束只存在数据库中，那么一旦系统结构变化、数据库方案变化、索引损坏或者产品路线调整，最高优先级记忆就会被工具实现反向绑架。

而将版本化 `Markdown` 作为基础层，有几个明显优势：

- 可直接阅读
- 可直接审计
- 可用 `Git` 版本化管理
- 可脱离当前系统单独保存和迁移
- 可在完全重构后继续作为新系统输入
- 便于按项目、按事务独立整理

这与当前已经确认的“高优先级记忆必须支持脱离当前实现路径重新评估”完全一致。

### `Markdown` 基础层的建议形态

当前更合理的方向是：

- 不同项目和不同事务使用目录隔离
- 每个项目或事务都应具备清晰命名
- 关键记忆内容以 `Markdown` 文档保存
- 标签、分类、状态等结构信息优先使用 `Markdown` 元数据标记
- 所有高优先级记忆都应保留原文，不允许只保留数据库投影结果

这意味着系统未来即使完全脱离当前程序实现，仍然可以通过文件树直接重新理解最重要的一批记忆。

### 数据库层的定位

数据库层仍然有价值，但它的定位应当非常明确：

- 用于加速读取
- 用于结构化查询
- 用于标签筛选
- 用于状态聚合
- 用于评估辅助
- 用于向量检索或语义召回

数据库层不应成为原始需求和关键记忆的唯一落点。

换句话说：

- `Markdown` 是基础记忆层
- `Git` 是版本化与审计层
- `SQLite` 是本地增强读写层
- 向量能力是检索增强层

### 为什么 `SQLite` 路线有价值

你提出“基于增强版 `SQLite` 提供，并考虑支持向量数据库能力”的方向，是合理的。

它的现实价值主要体现在以下几点：

- 本地部署和迁移成本低
- 非常适合单机或轻量系统起步
- 便于和文件系统共存
- 便于按项目或按事务独立建库
- 读写、过滤、聚合、索引能力足够强
- 后续可通过扩展支持向量检索，而不必一开始就引入更重的外部数据库

对于你当前这个项目来说，这种路线非常符合“先把高优先级记忆体系做扎实，再逐步增强检索和协作能力”的推进顺序。

### 按项目或按事务分库的价值

支持按项目名或事务名创建独立数据库，这个思路有明确价值。

它至少解决三个问题：

- 分类边界更清晰，不同项目的记忆不会自然混杂
- 单库数据规模可控，降低 `SQLite` 在大数据量场景下的压力
- 迁移、归档、备份、重建、实验都更灵活

同时，这也与“高优先级记忆可以脱离当前实现路径重新评估”的目标一致，因为项目级或事务级分隔更容易做抽取、复制、平行试验和重构。

### 这条路线的边界

虽然这条路线很有价值，但当前阶段仍应明确几个边界：

- 不应把数据库结构过早当成最终产品结构
- 不应因为要做向量检索而削弱 `Markdown` 原文的基础地位
- 不应让标签、状态、分类只存在数据库而不回写基础文档
- 不应让“方便查询”反过来主导“如何记录需求原文”

因此，当前更准确的判断应当是：

**版本化 `Markdown` 记忆文档是基础层和唯一真相源，`SQLite` 及其向量增强能力是服务于它的派生层。**

## 未来必须有两个核心视图

这个产品未来不应只有一个聊天流视图。

至少应当有两个核心视图。

### 1. 会话视图

用于：

- 看 agent 输出
- 看用户纠偏
- 继续对话
- 执行暂停、继续、分叉等操作

### 2. 需求视图

用于：

- 看原始需求基线
- 看需求增量历史
- 看当前有效约束
- 看成功标准
- 看偏离情况
- 看完成度证据

需求视图是系统避免退化成“更好看的聊天窗口”的关键。

## 核心评估逻辑必须围绕需求展开

未来所有执行结果，都应围绕三个问题持续评估。

### 1. 偏离检查

判断：

- 当前执行是否仍然符合原始需求和使用场景
- 如果偏离，偏离发生在哪一条要求上

### 2. 完成度检查

判断：

- 哪些成功标准已经满足
- 哪些部分仍然缺乏证据

### 3. 质量检查

判断：

- 即使方向没有偏离，输出质量是否足够
- 是否出现了失败信号

这三种检查必须是“需求中心”的，而不是“代码中心”的。

## 当前阶段最小方向范围

在进入更具体的设计之前，当前阶段最小应确认的方向范围应包括：

- 以会话为中心
- 以 Web 为主界面
- 保留现有 Agent
- 保存原始需求基线
- 保存需求增量
- 建立记忆分类与标签能力
- 建立偏离、完成度、质量三类评估逻辑
- 建立高优先级记忆可脱钩重评估的结构基础

当前阶段不需要立即确定：

- 最终数据库结构
- 最终 API 结构
- 插件架构细节
- conductor 集成方式
- 多 agent 自动编排细节

## 当前建议的推进顺序

如果方向成立，后续推进顺序应当是：

1. 先验证“需求记忆 + 监督纠偏”是否是正确的核心
2. 先围绕一个 Agent 类型验证监督会话模型
3. 再增加更多 Agent Adapter
4. 最后再考虑 workflow、编排和自动化层

这样可以避免过早优化错误层次。

## 当前结论摘要

当前方向可以概括为以下几点：

- 目标产品不是单纯工作流系统，而是 **需求记忆驱动的 Agent 协作平台**
- 它应当是 **Web 优先**
- 它应当保留 **现有 Coding Agent**
- 它的最高优先级是 **需求完整性**
- 它必须具备 **需求基线 + 需求增量 + 分类标签** 能力
- 它必须具备 **高优先级记忆脱钩重评估** 能力
- 偏离、完成度和质量，都必须回到需求视角判断
- `conductor` 更适合作为后续外围编排层，而不是第一阶段核心交互层

## 关于 Reasonix 作为底座的评估

当前新增判断是：

**Reasonix 是一个值得认真考虑的底座候选，而且从你的背景和目标来看，这个判断是合理的。**

### Reasonix 适合作为底座的理由

#### 1. 它同时具备 TUI 和桌面/Web 交互形态

这符合你当前的真实使用偏好：

- Web 端更适合展示、纠偏和整理
- TUI 仍然适合高频、低延迟、本地操作

从源码和文档看，`reasonix` 当前已经同时覆盖了：

- CLI / TUI
- 桌面端 `WebView`
- 基于 `HTTP + SSE` 的会话服务

因此，它比单纯 CLI 工具更接近“可扩展监督平台”的要求。

#### 2. 它已经有会话、历史和记忆相关能力

从源码和文档看，`reasonix` 已经具备以下方向上的基础：

- 会话历史读取
- 会话引用
- 记忆召回
- 记忆建议
- 记忆归档而不是硬删除
- 可追溯的会话与记忆管理

这与当前目标非常接近，因为你最看重的就是：

- 保留原始需求
- 保留纠偏记录
- 支持未来重评估

#### 3. 它的扩展性较好

从仓库结构和 `cmd/reasonix-plugin-example` 可见，`reasonix` 的插件能力并不是附带性质，而是一个明确暴露出来的扩展面。

这意味着后续可以考虑把你需要的外部能力做成：

- 内部模块
- 桌面增强功能
- MCP / JSON-RPC 风格插件
- 记忆或协作扩展

这比完全封闭的工具更适合作为长期底座。

#### 4. 它是 Go 编写，与你的技术背景高度契合

这一点不能低估。

如果你对 Go 十分熟悉，那么以下事情的成本会显著下降：

- 核心结构理解
- 会话层修改
- 持久化设计扩展
- 事件与状态管理扩展
- 打包、维护和长期演进

这会直接影响项目是否能真正长期推进。

#### 5. 它当前的 Web / Desktop 形态“不够完善”，反而可能是机会

如果一个系统已经非常重、非常复杂、非常固化，那么改造成本会更高。

而 `reasonix` 当前看起来：

- 已经具备基础能力
- 但还没有完全定型成难以改造的复杂平台

这反而意味着它更适合做定向改造和长期维护。

### Reasonix 作为底座的风险

虽然 `reasonix` 很有潜力，但仍然有几个需要明确记录的风险：

#### 1. 它原始定位仍然是 Coding Agent，而不是需求记忆平台

也就是说，你要做的核心系统能力，仍然需要自己补。

特别是以下部分：

- 原始需求基线模型
- 需求增量模型
- 高优先级记忆抽离
- 脱钩重评估机制
- 决策档案层

这些目前看起来并不是 `reasonix` 的中心定位。

#### 2. 它已有记忆能力，但不等于满足你的记忆模型

`reasonix` 已经有 session history 和 memory retrieval，但你要的不是一般意义上的“记忆召回”，而是：

- 可追溯的原始需求档案
- 可回退的决策记录
- 可重新审视的高优先级约束
- 面向未来重构的结构化记忆体系

这需要额外设计，不能直接把已有 memory 功能等同于你的目标系统。

#### 3. 它的桌面/Web 层虽然存在，但可能仍偏向原生 agent 界面

也就是说，它未必天然就是“监督驾驶舱”。

你很可能仍然需要重构或扩展它的交互层，尤其是：

- 需求视图
- 决策视图
- 偏离、完成度、质量评估视图
- 记忆抽取与重评估入口

### 当前判断

综合来看，当前判断是：

**Reasonix 适合作为第一优先级底座候选。**

但应当以这个前提推进：

**使用 Reasonix 作为执行与会话底层，不代表把产品定位限制为“Reasonix 桌面端增强版”。**

你要做的仍然是更上层的系统。

## 关于 Gitea / Forgejo 作为交互平台的评估

你提出的另一个交互场景是：

- 以 `Gitea` / `Forgejo` 这类仓库管理界面为基础
- 将 `issue`、`pull request`、评论流等作为主要交互入口

当前判断是：

**这个想法是可行的，而且非常值得保留，但它更适合作为“协作与审计表层”，而不适合作为第一阶段唯一主界面。**

### 这条路线的优点

#### 1. 所有推进过程天然可追踪

使用 `issue`、合并请求、评论流作为主载体，天然具备：

- 时间顺序
- 参与者记录
- 修改意见记录
- 决策流转记录
- 审批与拒绝记录

这与“有据可查”的目标高度一致。

#### 2. 非常适合作为纠偏历史和决策档案外壳

当用户的纠偏、agent 的输出、review 的意见都沉淀在仓库协作界面里时：

- 可读性强
- 易于回看
- 易于组织
- 易于团队协作

这对于长期项目尤其有价值。

#### 3. 它天然适合和代码变更关联

`issue` 与合并请求的语义，本来就贴近：

- 问题提出
- 方案讨论
- 实现推进
- 差异检查
- 合并决策

这一点和“需求到实现的映射”高度匹配。

### 这条路线的限制

#### 1. 仓库界面不是连续实时协作壳

它更像：

- 讨论与记录平台
- 状态与决策平台

而不是：

- 高频实时监督壳
- 即时插话式 agent 会话层

也就是说，它更适合沉淀，不一定适合作为最快速的实时控制面板。

#### 2. 以 `issue` / 合并请求为中心，容易天然偏向“代码协作”

你这个项目的长期目标，已经不只局限于开发工作。

如果未来还要扩展到日常工作、非代码任务或更一般的协作场景，那么：

- `Gitea` / `Forgejo` 这类界面的模型仍然偏代码仓库
- 它可能会限制系统未来的泛化能力

#### 3. 它适合做系统外壳的一部分，不适合独自承担全部内核能力

特别是下面这些能力，仍然不应完全依赖仓库界面：

- 需求记忆优先级模型
- 需求增量归档
- 高优先级记忆抽离
- 偏离、完成度、质量自动评估
- 会话级持续协作控制

### 当前判断

综合来看，当前更合理的判断是：

`Gitea` / `Forgejo` 方案不是错误方向，反而很值得纳入中长期结构。

但它更适合承担以下角色：

- 协作记录表层
- 审计与回放表层
- 决策归档表层
- 面向代码仓库的工作入口

而不应在第一阶段承担整个系统的实时会话中枢角色。

## 当前阶段对整体架构方向的补充判断

基于新增信息，当前更完整的方向判断如下：

### 1. 系统定位已经超过“驾驶舱”

现在更准确的说法应当是：

**这是一个需求记忆驱动的 Agent 协作平台。**

“驾驶舱”只是其中的交互层。

### 2. Reasonix 是当前最有现实可行性的底座候选

原因包括：

- 有 TUI 和 Desktop/Web 双形态
- 有会话和记忆基础
- 有插件扩展面
- Go 技术栈适合你长期维护

### 3. Gitea / Forgejo 很适合作为第二表层

未来很可能形成这样的分层：

- `Reasonix`：执行层与会话层底座

- `Gitea` / `Forgejo`：问题、决策、合并请求、审计与历史沉淀表层

### 4. 第一阶段仍然不应直接做成“仓库界面插件项目”

更合理的做法是：

- 先把需求记忆和监督会话模型跑通
- 再考虑把结果映射到 `issue` / 合并请求体系

这样可以避免一开始就被仓库平台的数据模型限制住。

## 关于 Hermes 作为长期在线中枢的评估

当前又出现了一个值得认真评估的方向：

- 是否可以让长期在线的 `Hermes` 充当交互中心
- 是否可以让它直接和 `codex`、`reasonix` 等工具交互
- 是否可以让它定期巡检 `Gitea` / `Forgejo` 中的 `issue` / 合并请求，并触发 `codex`、`reasonix` 推进任务

基于本机已安装的 `Hermes` 能力面和当前目标，结论是：

**这个方向很有价值，而且应该纳入整体架构考虑，但它更适合放在“长期在线协调与运营层”，而不是直接替代底层执行内核。**

### 当前可观察到的 Hermes 能力面

从当前本机 `hermes` 命令能力看，它已经覆盖了很多和“长期在线协调中枢”相关的能力：

- `gateway`
- `send`
- `cron`
- `webhook`
- `kanban`
- `dashboard`
- `sessions`
- `memory`
- `acp`

这说明它不是单纯的聊天工具，而是一个具备：

- 消息入口
- 调度能力
- 定时能力
- 任务板能力
- 仪表盘能力
- 长期运行能力

的代理系统。

这正是它值得被纳入评估的原因。

## Hermes 可以承担的三类角色

当前对 `Hermes` 的价值评估，建议分成三类角色，而不是把它笼统地视为“另一个 Agent”。

### 1. 消息与交互入口中心

这是 `Hermes` 当前最明显的价值之一。

如果它长期在线，并且已经通过 `gateway` 接入若干消息平台，那么它可以承担：

- 用户消息入口
- 通知出口
- 任务状态回传
- 异常告警
- 人工确认提醒

这一层价值非常高，因为它天然适合承担跨端通知和轻量交互。

对于你当前设想的系统来说，这意味着：

- 用户不一定必须总在主 Web 驾驶舱里
- 某些纠偏、确认、提醒、状态同步可以通过 `Hermes` 完成
- 长周期任务不必始终依赖前台界面常驻

### 2. 长期在线调度与巡检中心

这是 `Hermes` 的第二类重要价值。

由于它具备：

- `cron`
- `kanban`
- `gateway`
- `dashboard`

这一层能力，因此它非常适合承担下面这些任务：

- 定期巡检 `Gitea` / `Forgejo` 的 `issue` / 合并请求
- 定期生成任务摘要
- 检测长时间未推进的任务
- 发现需要重新纠偏的任务
- 把任务派发给某个执行器
- 把结果再发回指定渠道

这意味着在未来架构里，`Hermes` 很适合被放在“持续运行的运营调度层”。

### 3. 任务板 / 任务分发中枢

`Hermes` 已经自带 `kanban` 能力。

这一点很重要，因为你的长期目标已经不只是开发工作，还可能扩展到日常任务和更一般的工作推进。

如果未来需要：

- 任务分派
- 排队推进
- 定期巡检
- 多个执行器协作
- 将任务映射到某个项目、某个 profile、某个工作区

那么 `Hermes` 的任务板和调度能力就会很有价值。

换句话说，它可能不是“需求记忆内核”，但它很可能是“长期在线任务运营层”的有力候选。

## Hermes 不适合作为唯一底层执行内核的原因

虽然 `Hermes` 很有价值，但当前判断仍然不建议把它直接视为你唯一的底层执行核心。

原因如下。

### 1. 当前重点不是“做一个万能 Agent 中枢”，而是“保存需求与支持持续纠偏”

`Hermes` 的强项明显偏向：

- 长期在线
- 多入口消息
- 调度
- 看板
- 定时
- 多 profile 运作

但你当前最核心的问题仍然是：

- 原始需求完整保存
- 高优先级记忆抽离
- 纠偏记录
- 偏离、完成度、质量评估
- 将需求从既有技术历史中解耦

这一套系统性需求，目前并不能因为 `Hermes` 已经存在就自动成立。

### 2. Hermes 很强，但它的重心更像通用持续代理，而不是你当前定义的需求记忆平台

如果过早把 `Hermes` 放到最核心位置，风险是：

- 你会更容易围绕“如何调度 agent”展开
- 而不是围绕“如何定义与保存真实需求”展开

这会让系统重心偏向运营自动化，而不是偏向需求正确性。

### 3. 如果让 Hermes 直接与 Codex / Reasonix 交互，仍然要解决适配与控制问题

即使 `Hermes` 作为中枢，也仍然需要明确：

- 它如何调用 `codex`
- 它如何调用 `reasonix`
- 它如何接收执行结果
- 它如何中断、继续、回传会话转录记录
- 它如何将结果回写到你的需求记忆系统

所以它不是“免设计”的捷径，而是“值得利用的上层协调器”。

## Hermes 的最适合纳入的场景

当前最适合把 `Hermes` 纳入的场景，不是第一阶段的底层内核，而是下面这些中后期场景。

### 场景一：任务巡检与提醒

例如：

- 定期巡检 `Gitea` / `Forgejo` 中待处理 issue
- 发现长期未推进任务
- 发现长时间无人回复的合并请求
- 定时把摘要发到消息平台

这个场景的可用价值非常高，而且实现价值明确。

### 场景二：轻量交互入口

例如：

- 用户通过消息平台回复一句纠偏意见
- 系统记录该纠偏意见并关联到具体任务
- 必要时通知 Web 驾驶舱或执行器继续推进

这可以降低系统对“用户必须打开主界面”的依赖。

### 场景三：任务运营与派发

例如：

- 根据任务类型决定交给 `reasonix` 还是 `codex`
- 根据任务状态决定进入 review、等待、重试或回退
- 用 `Hermes` 的看板和 profile 把任务持续跑起来

如果未来系统进入多任务并行阶段，这一层会特别有价值。

### 场景四：异步协作回路

例如：

- `Hermes` 定时巡检 issue
- 判定某个 issue 值得推进
- 调用 `reasonix` 或 `codex`
- 收到结果后发回消息平台或记录到仓库系统
- 等待人类进一步纠偏

这条回路非常适合“长期在线系统”。

## Hermes 与 Gitea / Forgejo 的组合价值

如果把你前面提出的 `Gitea` / `Forgejo` 方向与 `Hermes` 结合，当前判断是这条路非常值得保留。

可以形成下面这种角色分层：

- `Gitea` / `Forgejo`：
  - 问题入口
  - 讨论沉淀
  - 合并请求审核
  - 决策归档

- `Hermes`：
  - 长期在线巡检
  - 通知与提醒
  - 任务派发
  - 轻量消息交互
  - 调度回路

- `Reasonix` / `Codex`：
  - 具体执行
  - 具体分析
  - 具体实现与修正

- 独立需求记忆 / 监督平台：
  - 保存原始需求
  - 保存纠偏与约束
  - 做偏离、完成度、质量评估
  - 提供需求视图和监督视图

这套分层的优点是：

- 每一层承担的职责清晰
- 没有要求单个系统承担全部责任
- 可以逐步演进

## 关于 OmniAgent 的评估

当前新增判断如下：

`OmniAgent` 对当前方向有现实价值，但它更适合作为**局部能力提供者**，而不适合作为整个系统的总底座。

### 当前确认到的 OmniAgent 特征

基于仓库当前公开内容，`OmniAgent` 至少具备以下明确特征：

- 当前版本是 `0.1.0`
- 项目状态偏早期，文档仍未完整上线
- 技术栈是 `Python 3.11+`
- 许可证是 `GPL-3.0-only`
- 具备 `CLI`、`Web UI`、`Gateway`、多渠道接入能力
- 具备基于 `Markdown` 文件发现、切块、`SQLite + FTS5` 索引、可选向量检索的记忆实现
- 具备“检索后只注入记忆提示”的上下文装配思路，而不是把完整记忆整包塞进系统提示词
- 具备从失败、反思、用户反馈中提取经验并回写规则的自进化实现

这些点里，和你当前方向最契合的，不是它的“全维自进化”宣传口径，而是它已经落地的这几类局部能力：

- `Markdown` 记忆发现与索引
- `SQLite` / `FTS5` / 可选向量检索
- 检索后选择性注入
- 从历史交互中提炼经验
- 多渠道网关雏形

### OmniAgent 对当前方向最有价值的部分

#### 1. 记忆索引与检索层

这是 `OmniAgent` 当前最值得认真借力的部分之一。

因为它已经具备一条与你当前判断高度接近的路径：

- `Markdown` 作为基础记忆文件
- 扫描工作区内的记忆文档
- 切块后写入 `SQLite`
- 用 `FTS5` 做全文检索
- 可选做向量增强
- 运行时只把命中的记忆提示注入上下文

这与当前已经确认的原则高度一致：

- `Markdown` 作为唯一真相源
- 数据库存取层只是派生层
- 运行时依赖检索，而不是整包记忆注入

因此，如果你的目标是“尽快跑通第一版记忆检索闭环”，`OmniAgent` 在这一层是有直接借力价值的。

#### 2. agent 辅助提取经验与纠偏记忆

`OmniAgent` 里还有一条很贴近你当前方向的实现思路：

- 从失败中提取经验
- 从反思中提取经验
- 从用户反馈中提取经验
- 把经验累积成可提升、可归档的规则

这和你刚刚强调的目标非常接近：

- 让 agent 帮忙评估
- 让 agent 帮忙提取高价值记忆
- 让系统支持回顾、提炼、矛盾检查
- 让系统具备一定自举能力

虽然它当前的落点更偏向 `AGENTS.md` 规则提升，不等于你要的完整风险导向记忆体系，但这条能力链本身是值得直接借力的。

#### 3. 多渠道交互入口雏形

`OmniAgent` 当前已经实现了：

- `Web UI`
- `Gateway`
- `Feishu`
- `Discord`
- `Telegram`
- `Webhook`

如果后面你希望快速试验“Web + 消息渠道 + 会话保持”的最小闭环，它也有一定现实价值。

但这一层当前不应被高估，因为你已经有 `Hermes`，而且 `Hermes` 在长期在线协调、任务巡检、消息中枢这条线上更贴合你当前设想。

### OmniAgent 不适合作为总底座的原因

虽然它有价值，但当前判断仍然不建议把 `OmniAgent` 直接当作整个系统的主底座。

主要原因如下。

#### 1. 它的中心目标不是你的“风险导向需求记忆系统”

`OmniAgent` 的中心叙事是：

- 自进化 Agent
- Reflexion
- Harness
- Skill 演化

而你当前的中心目标是：

- 保存原始需求
- 保存高风险纠偏
- 保存决策理由
- 支持回顾、重评估、重构
- 用记忆守住未来项目风险

两者有交集，但不重合。

如果直接把它当总底座，很容易让系统重心重新滑回“如何把 Agent 做得更强”，而不是“如何把需求与风险守住”。

#### 2. 它当前的记忆模型仍然偏工作区与 Agent 规则

你需要的是：

- 全局记忆
- 项目记忆
- 事务记忆
- 会话记忆
- 风险模式记忆
- 可回顾、可提炼、可重评估的关系体系

而 `OmniAgent` 当前更接近：

- 工作区记忆
- 会话辅助记忆
- 经验规则提升

这说明它可借力，但不能直接覆盖你的目标模型。

#### 3. 当前成熟度仍然偏早期

从仓库状态看，当前至少存在以下现实信号：

- 版本仍是 `0.1.0`
- 文档仍未完整上线
- 默认直接跑测试并不能开箱即用

这类信号说明它更适合作为可拆用的能力来源，而不是当前阶段唯一押注的主平台。

#### 4. `GPL-3.0-only` 许可证需要单独慎重评估

这一点不能忽略。

如果你未来希望这个新项目在许可证上保持更高自由度，那么直接复制、合并 `OmniAgent` 代码进入主项目，可能会带来明显约束。

因此，当前更稳妥的判断是：

- 可以借力其思路和实现
- 可以考虑以独立组件、独立服务、独立进程边界方式使用
- 但如果要做深度代码级整合，必须先把许可证影响评估清楚

### 如何充分使用 OmniAgent

如果目标是“借力搭积木”，而不是只借鉴思路，当前更合理的使用方式有三种。

#### 方式一：把 OmniAgent 当作记忆检索侧车

这是一种低耦合、高现实性的用法。

这非常适合你当前强调的“agent 帮忙评估和提取”。

#### 方式三：把 OmniAgent 当作前期渠道桥接原型

即：

- 在正式驾驶舱还没做完之前
- 借它的 `Web UI` 或消息网关先跑通一条交互链路
- 重点验证“记忆检索 + 纠偏 + 回顾提炼”闭环

但这条路线的定位必须清楚：

- 是原型借力
- 不是总架构押注

## 已确认判断

截至当前阶段，以下判断已经可以视为已确认判断：

- 要做的不是单纯工作流系统
- 要做的不是另一个新的 Coding Agent
- 要做的是一个以需求记忆为核心、以持续监督和连续纠偏为重点的 Agent 协作平台
- 第一优先级是保存原始需求、场景需求、成功标准、非目标和高优先级纠偏约束
- 记忆是否值得长期保存，核心判断标准应当是它对未来项目风险是否有高价值
- 原始需求原文必须永久保留，不能被自动摘要静默替代
- 后续纠偏必须作为需求增量单独记录，不能简单混入普通聊天历史
- 系统必须支持高优先级记忆脱离当前实现路径重新评估
- 版本化 `Markdown` 记忆文档应作为记忆基础层和唯一真相源
- 系统必须正式支持跨项目、跨事务复用的全局经验记忆
- 运行时应以“检索后选择性注入”为原则，而不是把整包记忆直接挂入会话
- 第一阶段主交互形态应当以 Web 为主
- `conductor` 当前更适合作为后续外围编排层，而不是第一阶段核心交互层
- `Reasonix` 当前是最值得优先评估的底座候选
- `Gitea` / `Forgejo` 适合作为协作记录、审计、归档表层
- `Hermes` 适合作为长期在线协调、巡检、通知和任务运营层
- `OmniAgent` 适合作为记忆检索增强与经验提炼辅助候选，而不适合作为总底座
- 会话可以作为自动提取记忆和归档的主要边界，但不能取代记忆的长期作用域划分
- 系统不仅要从会话中提取记忆，还应在需要时具备向执行器会话写入纠偏提醒和监督回复的能力

## 待验证假设

- `Reasonix` 是否足以作为第一阶段执行与会话底座
- `Reasonix` 现有会话、记忆、插件能力是否足以低成本扩展出你需要的需求记忆系统

- `Hermes` 与 `Gitea` / `Forgejo` 的组合，是否适合作为长期在线任务巡检与异步协作回路
- `SQLite` 的分库、索引、向量增强方案，是否足以支撑后续规模增长

- 系统是否能够逐步形成面向自身演进的自举式优化回路
- 需求记忆分类、标签、归档方式，是否能够在不牺牲灵活性的前提下保持严格可追溯

## 下一阶段：需求记忆模型方向

在方向已经获得初步确认之后，下一阶段最合理的切入点不是界面，不是编排，也不是数据库，而是先定义“需求记忆模型”本身。

因为只有先定义清楚“什么才算需求记忆”“哪些记忆正在生效”“哪些记忆只是历史参考”，后续的监督、纠偏、评估、回放、重构才会有稳定依据。

## 需求记忆模型首先要回答的问题

这一层至少要先回答以下问题：

- 系统到底要记录哪些类型的记忆
- 这些记忆分别属于全局、哪个项目、哪个事务、哪个会话
- 哪些记忆是原始基线
- 哪些记忆是后续增量
- 哪些记忆当前仍然有效
- 哪些记忆已经被替代、废弃或降级
- 当多条记忆冲突时，应该服从哪一条
- 当需要重新评估时，应该抽取哪一批记忆作为重新起盘的输入

如果这些问题没有先定义清楚，那么无论 Web 界面做得多好、数据库做得多快，系统都会退化成“有历史记录的聊天壳”。

## 需求记忆的根本筛选原则

当前需要进一步明确一个更高层原则：

**凡是对未来风险判断有高价值的内容，都应优先进入需求记忆体系。**

这里的“未来风险”以项目风险为核心，同时也覆盖重要事务中的方向性风险。它不只指技术失败，也包括：

- 方向跑偏
- 为短期体验妥协而违背项目初衷
- 需求理解被逐步污染
- 历史决策未被重新审视而持续放大代价
- 重构时丢失关键背景
- 错误经验反复出现

这意味着，系统不应只记录“你目前已经列举出来的几类记忆”。

更准确的说法应当是：

- 目前已经识别出来的记忆类型，只是第一批高频场景
- 未来还应允许继续纳入新的高风险记忆类型
- 记忆体系的扩展标准，不是“是不是常见字段”，而是“是否明显服务于未来风险判断与纠偏”

因此，这个系统的记忆模型必须是：

- 有核心原则
- 可持续扩展
- 允许新增记忆类别
- 但不允许偏离“服务未来风险判断”这个根本目标

## 需求记忆的最小对象

当前判断是：

**需求记忆系统的最小对象不应是消息，而应是“记忆条目”。**

原因很直接：

- 一条消息里可能同时包含需求、纠偏、约束、偏好、完成判断
- 单纯按消息保存，不利于后续按类型、优先级和有效性做判断
- 记忆系统必须能够把“会话中的一句话”提炼成“可持续生效的记忆条目”

因此，后续系统至少应区分：

- 消息
- 记忆条目
- 记忆条目之间的关系

消息是来源，记忆条目才是需求记忆系统真正用于评估和决策的对象。

## 需求记忆的四层作用域

当前更合理的作用域划分是四层，而不是只按单一会话保存。

### 1. 全局作用域

用于保存跨项目、跨事务、跨场景仍然具有复用价值的通用经验。

例如：

- 代码审阅经验
- 重构经验
- 测试经验
- 风险识别经验
- 常见跑偏模式
- 常见伪完成信号

这类记忆的特点是：

- 不绑定单一项目
- 不绑定单一事务
- 可以在很多地方重复产生价值
- 需要能够被任何项目或事务检索到

因此，系统必须正式支持“全局记忆”，而不能只支持项目内记忆。

### 2. 项目作用域

用于保存在整个项目周期内长期有效的内容，例如：

- 原始目标
- 使用场景
- 成功标准
- 非目标
- 长期约束
- 架构级关键决策

### 3. 事务作用域

这里的“事务”不应被误解为“某一次具体开发任务”。

更准确地说，它指一段相对独立、可命名、可归档、可回放的推进主题。

例如：

- 一次重构
- 一次功能推进
- 一次纠偏处理
- 一次架构重评估
- 一次需求澄清
- 一次日常工作处理
- 一次项目外部但仍需系统跟踪的重要事务

事务作用域用于承载“项目之下或全局之下、会话之上”的一批记忆。

它可以存在于某个项目内部，也可以存在于项目之外。

### 4. 会话作用域

用于保存某次具体交互和执行中的即时信息，例如：

- agent 当前输出
- 用户即时纠偏
- 本轮新增约束
- 当前完成判断
- 当前失败信号

会话作用域最容易变化，也最容易产生噪声，因此不能让它直接覆盖全局作用域、项目作用域和事务作用域中的高优先级基线。

## 会话既是提取来源，也是监督回复入口

如果后续接入的底座是 `Reasonix` 和 `OpenCode` 这类本身已经具备会话概念的执行器，那么会话不应只被当作记忆提取来源。

更准确的判断应当是：

**会话既是记忆提取来源，也是监督系统进入执行过程的主要入口。**

这意味着系统后续至少要具备两类能力：

### 1. 从会话中自动提取高价值记忆

系统可以在会话内的关键节点做自动提取，例如：

- 用户明确纠偏后
- agent 输出明显偏离信号后
- 用户确认某条关键判断后
- 某次任务完成或失败后
- 某段历史被识别为可提炼经验后

提取后的内容不应继续停留在原始消息层，而应被整理为正式记忆条目，并归入合适作用域。

### 2. 向会话中写入监督回复

系统还应具备向执行器原生会话中写回内容的能力，例如：

- 发送纠偏提醒
- 发送风险提示
- 发送需求补充
- 发送成功标准提醒
- 直接代表用户向当前 agent 追加澄清或修正

这说明监督系统不能只做旁观式索引器，还必须具备“受控插话”能力。

## 会话内监督回复的定位

这里必须明确一个边界：

监督系统写回会话，并不意味着它要夺走用户控制权，也不意味着它应当无约束地自动发言。

更合理的定位应当是：

- 默认以提醒、候选回复、纠偏提示为主
- 在明确授权的场景下支持自动回复
- 自动回复必须带有可追溯来源
- 自动回复应被记录为监督系统介入，而不是伪装成用户原话

否则系统很容易制造新的混乱来源。

因此，更准确的说法是：

- 用户仍然是最高优先级控制者
- 监督系统是可插话、可提醒、可代发的协作层
- 执行器仍然负责原生任务推进

## 这条能力对最终形态的意义

一旦加入这条能力，系统的最终形态就不再只是：

- 会话读取器
- 记忆归档器
- 回顾分析器

它还会成为：

- 会话监督者
- 纠偏提示者
- 风险拦截者
- 必要时的会话内协作回复者

这与前面已经确认的目标是一致的，因为你真正需要的不是纯粹的观察系统，而是一个能够持续纠偏、持续协作的监督系统。

## 下一阶段：会话接入模型方向

在确认“会话既是提取来源，也是监督回复入口”之后，下一层必须先定义的是“会话接入模型”。

这一层的目标不是先决定具体接口实现，而是先回答：

- 系统如何识别一个会话
- 系统如何进入一个会话
- 系统如何持续观察会话
- 系统何时提取记忆
- 系统何时发出提醒
- 系统何时允许自动回复
- 系统介入后如何保留清晰边界和可追溯性

如果这一层没有先定义清楚，后续无论接 `Reasonix` 还是 `OpenCode`，都会很容易变成“能读到一点消息，但不知道该怎么稳定协作”。

## 会话接入模型的基本判断

当前更合理的判断是：

**监督系统不应直接拥有执行器会话，而应以“附着在原生会话之上的协作层”方式接入。**

这意味着：

- `Reasonix` / `OpenCode` 继续拥有自己的原生会话
- 监督系统识别并附着到这些原生会话
- 监督系统读取事件、判断风险、提取记忆、在必要时写回提示
- 监督系统不应假装自己是执行器本身

这条边界很重要，因为它决定了后续系统不会轻易破坏执行器的原生使用体验。

## 会话对象的最小识别单元

当前建议，会话接入模型至少要稳定识别以下几个对象：

### 1. 执行器

用于区分当前会话来自哪个底座，例如：

- `Reasonix`
- `OpenCode`
- 后续可能加入的其他执行器

### 2. 会话标识

用于识别某一个原生会话。

它必须足够稳定，能够支持：

- 会话恢复
- 会话重连
- 会话回放
- 会话与记忆条目关联

### 3. 工作区

用于识别当前会话关联的代码目录、项目目录或事务工作区。

这是非常关键的关联维度，因为：

- 同一个执行器可以同时存在多个会话
- 同一个用户也可能在多个工作区并行推进不同任务

### 4. 归属锚点

用于判断当前会话归属于：

- 哪个项目
- 哪个事务
- 哪个场景

没有这一层，系统就很难把会话里抽出来的记忆正确归档。

## 会话接入后的三类运行状态

监督系统接入会话后，当前建议至少区分三类状态。

### 1. 观察状态

系统只读取和分析当前会话，不主动写回。

适用场景：

- 初始接入
- 低风险任务
- 用户只希望先记录和提取

### 2. 提醒状态

系统允许向会话提供提醒、候选回复或纠偏提示，但默认不自动代发。

适用场景：

- 出现潜在偏离
- 出现关键需求遗漏
- 出现需要提醒的成功标准
- 出现可能的风险操作

### 3. 代发状态

系统在明确授权条件下，可以直接向原生会话写回监督回复。

适用场景：

- 用户已明确授权该类场景自动介入
- 高风险偏离已经满足触发阈值
- 某些固定格式的纠偏回复可以稳定自动化

这三种状态不能混为一谈，否则系统不是太弱，就是过度干预。

## 会话事件模型

为了让会话接入模型可持续工作，当前建议先把系统关注的事件类型定义清楚。

至少应当包括：

- 用户新输入
- agent 新输出
- 工具执行完成
- 用户明确纠偏
- 用户明确确认
- 风险信号出现
- 任务完成
- 任务失败
- 会话暂停
- 会话恢复

这些事件并不等于最终 API，但它们决定了后续系统该在哪些时机触发：

- 记忆提取
- 风险评估
- 提醒生成
- 自动回复判断
- 评估文档更新

## 记忆提取触发点

当前建议，会话内的记忆提取不应只在“会话结束时”发生。

更合理的触发点是多点触发：

### 1. 即时触发

在出现高价值信号后立即提取，例如：

- 用户明确改方向
- 用户明确补约束
- 出现高风险偏离
- 用户明确确认某条决策

### 2. 阶段触发

在一个相对完整的阶段结束后提取，例如：

- 某轮实现完成
- 某轮 review 结束
- 某次纠偏处理结束

### 3. 会话结束触发

在会话暂停、关闭或长时间中断时，对本次会话做总结提取。

这种多点触发更符合你的目标，因为高价值记忆不一定等到会话结束才值得保存。

## 监督提醒触发点

会话写回提醒的触发点，应当比自动回复更宽。

当前建议至少包括：

- 当前输出与原始需求明显偏离
- 当前输出忽略了高优先级约束
- 当前实现只优化了短期体验，却可能违背项目初衷
- 当前会话重复出现已知错误模式
- 当前推进缺失完成证据，但 agent 已倾向宣布完成

这类场景非常适合先触发提醒，而不是立刻自动代发。

## 自动回复触发点

自动回复必须比提醒更严格。

当前建议只有在下面这类条件同时满足时，才应考虑自动回复：

- 触发条件明确
- 风险较高
- 回复模板或回复策略足够稳定
- 用户已经对该类场景授权
- 自动回复内容可以明确标注来源

如果这些条件不成立，更合理的做法仍然是：

- 给出候选回复
- 等待用户确认

## 会话写回的三种输出形态

当前建议，监督系统写回原生会话时，至少应支持三种输出形态。

### 1. 监督提醒

特点：

- 短
- 明确
- 不抢控制权

适合：

- 风险提示
- 成功标准提醒
- 关键约束提醒

### 2. 候选纠偏回复

特点：

- 系统生成一条可直接发送的纠偏内容
- 默认由用户确认是否发送

适合：

- 方向修正
- 范围澄清
- 技术约束补充

### 3. 自动代发回复

特点：

- 直接进入原生会话
- 需要明确授权和日志

适合：

- 已定义好的高风险拦截场景
- 已稳定模板化的提醒或约束补充

## 会话内身份与痕迹要求

监督系统一旦进入原生会话，后续所有介入都必须具备清晰身份和痕迹。

至少应满足：

- 系统介入内容必须能区分于用户原话
- 系统介入内容必须能区分于执行器原生输出
- 每次介入都要可追溯到触发原因
- 每次自动代发都要有授权依据

否则后续回顾时就会分不清：

- 哪句是用户说的
- 哪句是监督系统说的
- 哪句是执行器自己做出的判断

## 用户控制优先级

会话接入模型里，用户控制优先级必须高于自动化。

当前建议明确以下顺序：

- 用户直接回复
- 用户明确授权的自动化规则
- 监督系统提醒与候选回复
- 执行器原生持续推进

也就是说，监督系统应帮助用户维持方向，而不是取代用户成为真正的任务拥有者。

## 对 Reasonix 和 OpenCode 的接入含义

如果底座重点是 `Reasonix` 和 `OpenCode`，那么会话接入模型对它们的要求主要集中在以下几点：

- 能稳定识别原生会话
- 能读取会话内新增消息和关键事件
- 能在不破坏原生体验的情况下写回提示或回复
- 能把监督系统的介入痕迹保留下来
- 能把会话与工作区、项目、事务关联起来

因此，下一阶段真正需要验证的重点，不是“它们有没有会话”，而是：

- 它们的会话是否足够可接入
- 它们的会话是否足够可观察
- 它们的会话是否足够可写回

## 当前阶段对会话接入模型的结论

截至当前阶段，较准确的高层判断如下：

- 会话是最终形态里的关键接入单元
- 会话既是记忆提取来源，也是监督回复入口
- 监督系统应附着在原生执行器会话之上，而不是取代原生会话
- 记忆提取、提醒生成、自动回复应有不同触发条件和不同权限边界
- 用户始终保持最高优先级控制权
- `Reasonix` / `OpenCode` 的会话可接入性，将直接决定它们是否适合作为最终底座

## 对当前思路的进一步收束

基于你新增的判断，当前更准确的第一阶段思路应当进一步收束为：

- 不重复发明新的主会话视图
- 直接借用 `Reasonix` / `OpenCode` 已有的会话界面
- 监督系统只需要获取当前原生会话的消息上下文
- 监督系统以最低耦合方式附着在原生界面外侧工作

这意味着，第一阶段要做的不是“再造一个聊天产品”，而是：

- 读取当前原生会话
- 基于当前会话和已有项目记忆做提取与评估
- 生成纠偏提示或候选回复
- 在需要时把候选回复回填到原生输入框

这个收束是合理的，而且很重要，因为它会显著降低第一阶段复杂度。

## 当前消息上下文是否足够

当前判断是：

**第一阶段大概率只读取消息上下文就已经足够开始工作。**

这里的“消息上下文”至少应包括：

- 用户消息
- agent 消息
- 消息时间顺序
- 当前会话标识
- 当前工作区或项目锚点

在第一阶段，下面这些上下文不一定必须同步接入：

- 命令执行细节
- 文件读写细节
- 搜索细节
- 工具调用全过程

原因很明确：

- 你当前最重要的是需求约束、纠偏、记忆提取、候选回复
- 这些能力首先依赖“用户说了什么”和“agent 回了什么”
- 并不一定依赖完整工具轨迹

但这里仍然要保留一个补充判断：

- 工作区标识仍然很重要
- 项目或事务归属仍然很重要
- 如果未来发现某类纠偏强依赖工具轨迹，再考虑把工具上下文作为第二阶段增强接入

所以更准确的说法是：

**第一阶段可优先采用“消息上下文为主，工作区锚点为辅”的最小接入策略。**

## 监督系统是否需要自己的会话

你这里的直觉是对的，但需要稍微收紧表述。

当前更准确的判断不是“监督系统完全不需要自己的会话”，而是：

**监督系统不应创造独立于原生会话之外的主会话体系，但仍然需要一个附着在原生会话之上的影子会话状态。**

这个影子会话状态的作用不是替代原生会话，而是用于：

- 提高缓存命中率
- 记录本次监督过程中的中间判断
- 保持记忆检索结果的短期连续性
- 减少重复提取和重复分析
- 让用户切回旧会话时，监督系统也能恢复到相应上下文

因此，当前更合理的判断应当是：

- 原生会话由 `Reasonix` / `OpenCode` 维护
- 监督系统只维护“影子状态”
- 影子状态必须以原生会话标识为主键附着
- 影子状态不是新的真相源

这也说明，你提到的“为了提高缓存命中率，希望切回老会话时还能继续工作”，这件事是有价值的。

## 单用户多任务并行是必须支持的

你明确排除了多用户并行，这会显著降低复杂度。

但“一个用户多个任务并行”仍然必须正式纳入模型。

这意味着监督系统至少要稳定区分：

- 当前用户的多个项目
- 同一项目下的多个事务
- 同一执行器下的多个原生会话

如果这一层做不好，记忆提取和候选回复就会串线。

因此，单用户并不意味着可以忽略会话隔离，反而意味着：

- 会话隔离
- 项目隔离
- 事务隔离

必须做得很清楚。

## 两种监督模式的判断

你提出的两种模式是合理的，而且非常适合第一阶段。

### 1. 手动触发模式

特点：

- 用户点击一次才工作一次
- 读取当前会话上下文
- 读取已有项目记忆
- 先做一次记忆提取
- 再评估是否需要纠偏
- 分类、标签、存储候选需要用户确认
- 纠偏内容和候选回复需要用户点击后才回填输入框

这是当前最稳妥的起步模式。

它的优点是：

- 风险最低
- 噪声最容易控制
- 最适合先验证“提取是否有价值”“纠偏是否有价值”

### 2. 托管模式

特点：

- 由前端开关控制
- 默认关闭
- 依赖前端页面常驻
- 每次 agent 停止时触发一次监督工作

这也是合理的，但它本质上已经比手动模式更进一步。

它的优点是：

- 用户负担更低
- 更适合连续协作
- 更容易形成“每轮停止就自动复盘和纠偏”的节奏

它的主要限制是：

- 依赖前端常驻
- 页面关闭后能力失效
- 如果事件钩子不稳定，容易漏掉触发点

因此，当前更合理的优先顺序应当是：

- 先做手动触发模式
- 再扩展托管模式

## 前端常驻加独立服务是很强的第一阶段路径

你提出“也许后端不用耦合接入，而是自己有一个服务，前端常驻工作”的判断，我认为这条路线非常有价值，而且很可能是当前最优的第一阶段方案。

它的关键优势包括：

- 对 `Reasonix` / `OpenCode` 后端最低耦合
- 不需要先深入改造底座后端
- 后续替换任意底座代价更小
- 监督系统可以独立演进
- 更适合做浮动按钮式增强界面

如果这条路成立，那么第一阶段真正需要的接入点可能非常少：

- 当前原生会话的消息列表
- agent 停止事件
- 原生输入框回填能力
- 当前工作区或项目标识

这比从一开始就要求深度后端接入要现实很多。

## 浮动按钮式监督界面是合理的

你提到“监督系统的前端使用浮动按钮界面”，这在当前阶段是合理的。

因为你现在最需要的不是完整重造界面，而是把监督能力叠加到现有会话产品上。

这种方式特别适合承载：

- 一键提取记忆
- 一键评估是否偏离
- 查看候选标签与分类
- 查看候选纠偏回复
- 一键回填输入框
- 开关托管模式

这与“低耦合、低侵入、可替换”的目标非常一致。

## 监督入口形态的进一步细化

基于你新增的设想，当前更合理的判断是：

**监督系统的入口不应只有一种形态，而应采用“单按钮 -> 快捷控制区 -> 展开面板”的渐进式结构。**

这条判断很重要，因为监督系统并不是一个纯展示组件，它同时承担：

- 提取触发
- 评估触发
- 候选回复展示
- 托管开关
- 记忆归档确认
- 风险提醒展示

如果一开始就只有完整面板，干扰会太强。

如果一开始只有一个按钮，又会导致高频操作过深。

因此，更合理的结构是三层。

### 1. 单按钮层

这是默认最收敛的入口形态。

它的职责应当非常单一：

- 显示监督系统是否可用
- 显示当前是否存在未处理提醒
- 点击后展开快捷控制区或完整面板

单按钮层的目标不是承载复杂操作，而是：

- 最低侵入
- 最低视觉干扰
- 最容易挂接到原生会话界面

因此，单按钮更像“监督入口点”，而不是“监督操作面板”。

### 2. 多按钮快捷控制区

如果单按钮展开后直接进入完整面板，很多高频动作会过重。

因此当前很适合加入第二层，也就是快捷控制区。

这一层最适合承载高频且低歧义的动作，例如：

- 立即提取
- 立即评估
- 查看提醒
- 候选回复
- 托管开关

这一层的价值很高，因为它可以解决两个问题：

- 常用操作不必每次都进入完整面板
- 用户可以快速知道当前监督系统能做什么

因此，多按钮区更适合作为：

- 高频动作区
- 轻量状态区
- 面板前的中间层

### 3. 展开面板

完整展开面板应当承载更复杂、更需要阅读和确认的内容，例如：

- 本轮提取出的候选记忆
- 候选分类和标签
- 偏离、完成度、质量评估结果
- 候选纠偏回复
- 监督系统的介入理由
- 正式归档确认

这一层适合做完整控制，但不适合承担所有高频动作。

因此，更准确的定位是：

- 单按钮负责进入
- 快捷区负责高频动作
- 面板负责复杂决策和确认

## 为什么这种三层结构是合理的

这种结构和你当前的产品目标是高度一致的。

因为监督系统的行为本来就存在明显分层：

- 有些动作只需要快速触发
- 有些动作只需要轻量提醒
- 有些动作必须完整查看和确认

如果把这些不同层级的动作全堆到一个入口里，会出现两个问题：

- 要么过重
- 要么过浅

而三层结构恰好对应：

- 最小入口
- 高频控制
- 深度控制

## 第一阶段最适合的入口组合

当前更推荐的第一阶段组合不是一次性把三层都做满，而是做一个可渐进扩展的最小版本。

当前建议顺序如下：

### 第一阶段最小版本

- 单按钮
- 点击后直接展开轻量面板

原因：

- 最容易做
- 最容易验证是否有用
- 最不容易把 UI 做得过重

### 第一阶段增强版本

- 单按钮
- 单按钮展开为多按钮快捷区
- 快捷区再进入完整面板

这个版本适合在你已经确认高频操作稳定之后再引入。

因此，当前不建议一开始就把快捷区、完整面板、复杂状态全做满。

## 按功能划分的界面职责

为了避免后面界面失控，当前建议先把三层的职责严格分开。

### 单按钮职责

- 进入监督系统
- 显示状态
- 显示提醒数量或风险信号

### 快捷控制区职责

- 触发提取
- 触发评估
- 查看候选回复
- 开关托管模式

### 完整面板职责

- 查看候选记忆条目
- 查看候选标签与分类
- 查看偏离、完成度、质量评估
- 查看候选回复详情
- 确认归档
- 确认是否回填输入框

这条职责分离非常重要，因为它会直接影响后续界面是否清晰。

## 这套入口形态对手动模式和托管模式的适配

这套结构对两种模式都适配得很好。

### 对手动模式

最自然的路径是：

- 用户点击单按钮
- 进入快捷区或面板
- 手动触发提取和评估
- 查看候选结果
- 决定是否回填

### 对托管模式

最自然的路径是：

- 单按钮持续显示状态
- 快捷区承担托管开关
- 面板显示托管运行后的提取结果、提醒结果和候选回复

也就是说，这套入口形态并不会和两种模式冲突，反而刚好把它们分层表达出来。

## 当前思路下最需要避免的问题

虽然这个方向是对的，但仍然需要避免几个典型问题。

### 1. 单按钮承载过多语义

如果单按钮同时想表示：

- 是否连接成功
- 是否有风险
- 是否正在托管
- 是否有候选回复
- 是否有未确认记忆

它会很快变得难以理解。

因此，单按钮的状态语义必须克制。

### 2. 快捷区变成第二个复杂面板

快捷区的目标是高频、低歧义。

如果把：

- 详细解释
- 长文本候选
- 多层确认

都塞进去，它就会失去意义。

### 3. 面板过重导致第一阶段验证变慢

你当前还在验证整体路线。

因此第一阶段完整面板更应该关注：

- 是否真能帮助提取
- 是否真能帮助纠偏
- 是否真能帮助回填

而不是过早做成一个复杂控制台。

## 当前对监督入口形态的结论

综合判断如下：

- 你的这个设想是成立的
- 监督入口采用“单按钮 -> 快捷控制区 -> 展开面板”的渐进式结构是合理的
- 单按钮适合做最低侵入入口
- 快捷控制区适合做高频动作层
- 完整面板适合做复杂查看和确认层
- 第一阶段不应一次做满三层，而应先做“单按钮 + 轻量面板”的最小验证版本

## 当前思路的主要风险

虽然这条路线很强，但仍然需要明确几个风险。

### 1. 前端事件是否足够稳定

如果最终接入高度依赖页面事件，那么需要确认：

- 能否稳定识别 agent 停止
- 能否稳定获取当前会话消息
- 能否稳定回填输入框

如果这些事件不稳定，托管模式就会很脆弱。

### 2. 页面关闭后托管能力失效

如果托管模式依赖前端常驻，那么它天然不是完整的长期在线系统。

这意味着：

- 第一阶段可以接受
- 但长期仍可能需要与 `Hermes` 之类长期在线协调层配合

### 3. 影子状态不能失控膨胀

既然监督系统要维护附着在原生会话上的影子状态，就必须避免：

- 影子状态变成第二套真相源
- 缓存与正式记忆混淆
- 切换会话时把短期缓存错误带入别的任务

因此必须明确：

- 正式记忆归档是正式层
- 影子会话状态只是短期工作缓存层

## 当前对这条思路的结论

综合判断如下：

- 这条思路是成立的
- 它比“深度后端耦合接入”更适合作为第一阶段方案
- 第一阶段只读取消息上下文，大概率就足够开始验证价值
- 监督系统应维护附着于原生会话的影子状态，而不是创建新的主会话体系
- 手动触发模式应先于托管模式
- 前端常驻加独立服务、浮动按钮叠加原生会话，是当前非常值得优先推进的低耦合实现路径

## 第一阶段最小工作流

如果按当前思路推进，第一阶段最小工作流可以收束为以下顺序。

### 手动模式

1. 用户在原生会话中推进 `Reasonix` 或 `OpenCode`。
2. 用户点击监督按钮。
3. 监督系统读取当前会话消息上下文和工作区锚点。
4. 监督系统读取相关项目记忆和全局经验记忆。
5. 监督系统提取高价值内容，生成候选记忆条目。
6. 监督系统评估是否偏离、是否完成、是否存在质量风险。
7. 监督系统生成候选纠偏回复或提醒。
8. 用户确认后，候选内容回填到原生输入框。
9. 用户决定是否发送。
10. 最终的记忆条目、标签和分类在用户确认后正式落档。

### 托管模式

1. 用户打开托管开关。
2. 原生会话继续推进。
3. 每次 agent 停止后，监督系统自动读取当前会话消息上下文。
4. 监督系统重复执行提取、评估、候选回复生成。
5. 候选回复先进入候选框或缓冲区。
6. 若用户保持授权且规则满足，可自动回填或自动代发。
7. 会话停止事件结束后，监督系统将本轮记忆正式归档。

## 第一阶段工作流的核心原则

这条工作流必须坚持几个原则：

- 监督系统只做最小必要介入
- 先提取，再评估，再回复
- 先候选，再确认，再落档
- 默认人工确认优先
- 自动化只在规则稳定后放开

这会保证系统既能工作，又不会过早失控。

## 继续下一阶段设计之前必须确认的问题

如果下一步继续推进会话接入模型，那么首先要确认的不是具体接口，而是下面这些高层问题：

- `Reasonix` 当前是否已经暴露足够稳定的会话读取边界
- `Reasonix` 当前是否已经暴露足够稳定的会话写回边界
- `OpenCode` 当前是否已经暴露足够稳定的会话读取边界
- `OpenCode` 当前是否已经暴露足够稳定的会话写回边界
- 哪些提醒场景只应生成候选回复
- 哪些高风险场景允许进入自动代发
- 监督系统介入内容在原生会话中应如何标识

只有这些问题基本明确后，后续才适合继续进入更具体的会话接入设计。

## 需求记忆的核心文档类型

为了让版本化 `Markdown` 体系能够真正承担唯一真相源的角色，当前建议至少区分以下几类文档。

### 1. 基线文档

用于保存最原始、最高优先级、最不可静默改写的内容：

- 原始需求
- 使用场景
- 成功标准
- 非目标
- 边界条件

这类文档一旦建立，后续只能通过增量修正解释，不能被静默重写。

### 2. 增量文档

用于保存后续新出现的修正信息：

- 新增约束
- 明确纠偏
- 优先级变化
- 范围变化
- 场景修正

这类文档的价值不在于“补一句说明”，而在于为系统提供“要求是如何变化的”这条时间线。

### 3. 决策文档

用于保存做过的关键判断：

- 技术选型
- 架构取舍
- 二次开发判断
- 接入方式判断
- 放弃某条路线的理由

这类文档必须保留理由，而不只是结论。

### 4. 评估文档

用于保存阶段性判断结果：

- 是否偏离
- 完成度如何
- 当前质量如何
- 哪些证据支持当前判断
- 哪些风险尚未解除

这类文档是“需求视图”能够成立的关键组成部分。

### 5. 证据文档

用于保存支持结论的依据：

- 关键 agent 输出摘录
- 用户明确确认
- 关键变更说明
- 关键测试结果
- 关键对比分析

这类文档的目标不是堆材料，而是保证“完成”“偏离”“可接受”这些判断都有可回溯依据。

### 6. 经验文档

用于保存能够跨场景复用的经验性记忆：

- 通用审阅经验
- 通用重构经验
- 通用测试经验
- 通用风险模式
- 通用纠偏模式

这类文档通常更适合进入全局作用域，但在必要时也可以由具体项目或事务沉淀后再被提炼上升为全局经验。

## 需求记忆的有效性规则

需求记忆系统必须能区分“存在过”与“当前生效”。

当前建议至少建立以下规则：

- 基线文档默认持续生效
- 增量文档必须明确它修正的是哪一类内容
- 新增约束可以覆盖旧约束，但不能抹掉原始基线原文
- 决策文档必须能够标记为有效、失效、废弃、待重评估
- 评估文档默认是阶段性结论，不应被当作长期约束直接继承

换句话说，系统需要的是“可追溯的有效性”，而不是“越新的内容自动越正确”。

## 需求记忆的关系模型

当前阶段虽然不需要落到数据库表结构，但关系类型需要先定义清楚。

至少应当支持以下几种关系：

- `源自`：某条记忆源自哪次用户输入、哪次 agent 输出、哪次人工整理
- `修正`：某条增量修正了哪条基线或旧增量
- `支撑`：某条证据支撑哪条评估或决策
- `替代`：某条记忆明确替代旧记忆
- `关联`：某条记忆与哪次事务、会话、代码变更相关
- `抽取自`：某条高优先级记忆是从哪段会话中抽取出来的
- `提炼为`：某条项目或事务记忆被提炼为全局经验
- `命中风险`：某条记忆对应哪类风险模式

如果没有这一层关系定义，后续就很难回答“为什么当前系统会这样判断”。

## 记忆进入会话上下文的原则

这里还需要明确一个容易被误解的问题：

虽然 `Markdown` 文档是唯一真相源，但这不意味着系统应当把完整 `Markdown` 内容直接附加到每次会话中。

当前更合理的原则应当是：

- 基础记忆长期保存为文档
- 运行时按问题检索相关记忆
- 根据风险权重、需求权重、经验权重筛选注入内容
- 只把当前问题真正相关的记忆片段送入模型上下文

这条原则很重要，因为它同时解决三个问题：

- 节省 `token`
- 提升处理速度
- 避免无关记忆分散模型注意力

因此，系统未来应更偏向：

- “检索后选择性注入”

而不是：

- “把整包记忆长期挂在会话上”

换句话说，唯一真相源与运行时上下文，不应被混为一谈。

## 记忆提取不能完全依赖人工整理

你前面提到希望让 agent 帮忙评估和提取，这个方向是合理的，而且价值很高。

因为高风险记忆往往并不是用户每次都会显式手工归档的。

因此，系统后续应当考虑支持下面这类能力：

- 从会话中识别高风险信息
- 从纠偏中提取可持续生效的约束
- 从 review 中提取通用经验
- 从失败案例中提取风险模式
- 从重构过程中提取未来可复用的判断依据

但这里仍然要保留一个边界：

- agent 可以帮助提取
- agent 可以帮助归类
- agent 可以帮助提出“值得记忆”的候选项
- 但高优先级记忆仍应具备可审查、可确认、可追溯的落档过程

否则系统会很容易积累噪声记忆。

## 系统必须支持回顾、提炼和矛盾检查

你提到的另一个重要场景也应明确纳入：

系统不应只负责“记住”，还应支持对既有记忆、历史操作、历史纠偏做回顾和提炼检查。

这个能力至少应支持：

- 回顾同一项目中已经出现过的纠偏历史
- 检查不同阶段之间是否存在矛盾要求
- 检查多个增量是否在表达同一件事
- 发现重复出现的风险模式
- 把零散历史提炼成更稳定的经验记忆

这说明需求记忆系统不只是存储系统，还必须具备“历史再审视”能力。

## 系统应考虑支持自举式优化

当前还应正式纳入一个重要判断：

**这个系统应当具备自举潜力。**

这里的自举，不是指单纯用自己写自己的代码，而是指：

- 系统能够保存自己的原始需求
- 系统能够保存自己演进过程中的纠偏和决策
- 系统能够把自己的问题场景再次纳入自身记忆体系
- 系统能够定期回顾自己的历史偏差、风险和错误判断
- 系统能够基于这些内容继续优化自己的架构设计策略

这意味着，后续每一次围绕本系统发生的问题、重构、偏离、纠偏，本身都应当成为本系统的学习材料和评估材料。

如果这一点成立，那么这个项目未来优化的对象就不只是：

- 技术实现
- 功能扩展
- 局部修补

还包括：

- 需求模型是否准确
- 风险模型是否准确
- 记忆提取规则是否准确
- 架构策略是否需要重新调整

## 需求记忆模型的核心价值

如果这套模型建立起来，它至少能稳定支持以下能力：

- 从会话中抽取长期有效的要求
- 从历史中抽取高风险经验并提升为全局记忆
- 判断当前执行依据的是哪一版要求
- 区分高优先级约束和低优先级实现偏好
- 在发生偏离时快速定位偏离的是哪条要求
- 在运行时只检索并注入当前真正相关的记忆
- 对历史纠偏和历史决策做回顾、矛盾检查与经验提炼
- 在需要重构时抽出最重要的一批记忆重新起盘
- 让系统把自身演进历史也纳入后续优化依据
- 在多项目、多事务并行时保持边界清晰

这正是你当前整个项目最需要先守住的部分。

## 当前阶段不应过早细化的内容

即使已经进入需求记忆模型阶段，下面这些内容仍然不应过早细化：

- 具体文件命名规范
- 具体元数据字段全集
- 具体索引结构
- 具体数据库表结构
- 具体向量切分策略
- 具体 UI 交互流程

当前阶段更重要的是先把“风险导向原则、记忆对象、作用域、文档类型、有效性规则、关系类型、检索注入原则、自举回顾能力”这几部分定义稳定。

## 下一阶段：记忆文档分类体系与目录规则

在需求记忆模型已经初步稳定之后，下一步最需要推进的不是数据库表，而是：

- 记忆文档分类体系
- 目录层级规则
- 文档归档边界
- 项目 / 事务 / 全局之间的分隔方式

因为只有这一层先稳定下来，后面的：

- `Markdown` 真相源
- `Git` 版本化
- `SQLite` 索引
- 向量检索
- 记忆提取与回填

才会有清晰的承载结构。

## 目录设计的基本判断

当前更合理的判断是：

**目录结构首先服务于记忆边界清晰，其次才服务于检索方便。**

换句话说，目录设计最优先要解决的不是“怎么搜得快”，而是：

- 哪些记忆属于全局
- 哪些记忆属于某个项目
- 哪些记忆属于某个事务
- 哪些是正式归档
- 哪些只是会话阶段候选

如果这一层不清楚，后面索引再强，也只是更快地搜索混乱内容。

## 当前建议的顶层目录分层

当前建议至少采用四层顶层分区。

### 1. `global/`

用于保存跨项目、跨事务复用的高价值经验与规则。

适合放入：

- 审阅经验
- 重构经验
- 测试经验
- 风险模式
- 常见偏离模式
- 通用纠偏模板

这部分内容的特点是：

- 不依附单一项目
- 不依附单一事务
- 未来很多地方都可能再次命中

### 2. `projects/`

用于保存具体项目的正式记忆体系。

适合放入：

- 原始需求
- 场景需求
- 成功标准
- 非目标
- 项目级约束
- 项目级决策
- 项目内事务归档入口

这是后续最重要的业务目录之一。

### 3. `matters/`

用于保存不属于某个项目、但仍然值得长期跟踪和重评估的重要事务。

这条目录很重要，因为你已经明确：

- 事务不一定属于项目
- 事务甚至可能不属于开发工作

因此，不能把所有事务都硬塞进项目目录。

### 4. `inbox/`

用于保存尚未正式归档、仍待提炼确认的候选内容。

适合放入：

- 会话自动提取候选
- 待确认标签
- 待确认纠偏记录
- 待提炼经验

这层目录的目标不是长期保存，而是给“正式归档前的缓冲区”一个稳定位置。

## 项目目录的建议骨架

对于 `projects/` 下的单个项目，当前建议优先采用固定骨架，而不是完全自由堆放。

例如：

```text
projects/
  <project-slug>/
    README.md
    baseline/
    increments/
    decisions/
    evaluations/
    evidence/
    sessions/
    matters/
    archives/
```

这个骨架的意义如下。

### `README.md`

用于保存这个项目的总体说明和目录导航。

至少应说明：

- 项目名称
- 当前状态
- 主要目标
- 关键目录说明

### `baseline/`

用于保存最高优先级、最不可静默改写的项目基线。

适合放入：

- 原始需求
- 使用场景
- 成功标准
- 非目标
- 边界条件

### `increments/`

用于保存后续新增或修正的要求。

适合放入：

- 新约束
- 新限制
- 方向纠偏
- 优先级变化
- 范围变化

### `decisions/`

用于保存关键决策和决策理由。

适合放入：

- 技术选型
- 架构决策
- 接入方式判断
- 放弃某路线的原因

### `evaluations/`

用于保存阶段性评估。

适合放入：

- 偏离评估
- 完成度评估
- 质量评估
- 阶段性风险评估

### `evidence/`

用于保存支撑判断的证据材料。

适合放入：

- 关键输出摘录
- 关键测试结论
- 关键对比结论
- 关键人工确认

### `sessions/`

用于保存与原生会话绑定的监督侧记录。

适合放入：

- 会话级提取记录
- 会话级监督介入摘要
- 会话级候选回复记录

需要明确：

- 这里不是原生会话本身的唯一保存地
- 而是监督系统附着在会话上的归档痕迹

### `matters/`

用于保存这个项目内部的事务目录入口。

适合放入：

- 某次重构
- 某次纠偏
- 某次评估
- 某个独立推进主题

### `archives/`

用于保存已失效、已终止、已完成但仍需保留的历史内容。

这层目录很重要，因为：

- 不能把失效内容直接删除
- 也不能让它继续混在当前有效内容里

## 事务目录的建议骨架

无论事务位于 `projects/<project>/matters/` 下，还是位于顶层 `matters/` 下，当前都建议采用相近骨架。

例如：

```text
matters/
  <matter-slug>/
    README.md
    baseline/
    increments/
    decisions/
    evaluations/
    evidence/
    sessions/
    archives/
```

事务目录和项目目录相似，是合理的。

原因是事务本身也可能拥有：

- 初始目标
- 过程纠偏
- 决策
- 评估
- 会话
- 归档

不同点在于：

- 项目目录偏长期
- 事务目录偏阶段性

## 全局目录的建议骨架

对于 `global/`，当前更适合采用主题型分区，而不是项目式分区。

例如：

```text
global/
  review/
  refactor/
  testing/
  risk-patterns/
  correction-patterns/
  prompts/
  archives/
```

这样做的好处是：

- 更适合跨项目复用
- 更适合被检索层直接命中
- 更适合后续从项目经验中向上提炼

## `inbox/` 的定位必须严格

`inbox/` 很容易失控，因此必须明确边界。

它的定位应当是：

- 临时候选区
- 待确认区
- 待提炼区

而不应成为：

- 第二套长期正式记忆目录
- 什么都先丢进去以后再说的垃圾区

因此更合理的规则是：

- 进入 `inbox/` 的内容必须带来源
- 必须有明确待处理状态
- 应尽量在有限周期内进入正式目录或归档目录

## 文档分类与目录的对应关系

为了避免“类型”和“目录”混淆，当前建议明确：

- 文档类型回答“这是什么内容”
- 目录层级回答“这份内容属于哪里”

例如：

- 一份“决策文档”可能位于 `projects/<project>/decisions/`
- 一份“决策文档”也可能位于 `matters/<matter>/decisions/`
- 一份“经验文档”更可能位于 `global/review/` 或 `global/risk-patterns/`

这条区分非常重要，因为它能防止后续目录结构和内容类型互相污染。

## 当前建议的命名原则

当前阶段不必把命名规则细化到字段级，但高层命名原则应先确定。

建议至少遵守：

- 目录名稳定、简短、语义明确
- 项目和事务使用可读 `slug`
- 不依赖中文标题作为唯一机器标识
- 文件名优先表达内容类型和主题，而不是临时感想

例如，当前更适合：

- `baseline/original-requirements.md`
- `increments/2026-06-25-scope-correction.md`
- `decisions/2026-06-25-choose-reasonix-as-runtime-base.md`

而不是：

- `new.md`
- `thoughts.md`
- `important.md`

## 当前建议的正式层与候选层分离规则

为了减少噪声，当前建议明确区分两种内容：

### 正式层

特点：

- 已确认
- 已归档
- 可以作为正式判断依据

适合进入：

- `baseline/`
- `increments/`
- `decisions/`
- `evaluations/`
- `evidence/`

### 候选层

特点：

- 刚提取
- 待确认
- 待分类
- 可能被放弃

适合进入：

- `inbox/`
- `sessions/` 中的候选部分

这条分离规则非常重要，因为它可以防止自动提取内容直接污染正式记忆。

## 当前建议的项目与事务关联规则

因为你特别强调“事务不一定属于项目”，所以必须先把关联规则定清楚。

当前建议如下：

- 某事务明确属于某项目时，优先挂到对应项目下
- 某事务与多个项目相关时，可以作为独立顶层事务存在
- 某事务完全不属于项目时，直接进入顶层 `matters/`
- 全局经验不进入项目或事务目录，而是进入 `global/`

这样做的好处是：

- 不会强行把不属于项目的事务塞进项目
- 也不会让项目相关事务漂浮在全局层

## 当前建议的目录规则核心价值

如果这一版目录规则成立，它至少能稳定支持下面这些能力：

- 高优先级记忆的长期稳定归档
- 项目与事务边界清晰
- 全局经验可持续积累
- 候选内容与正式内容清晰分离
- 后续 `SQLite` 和向量检索有稳定的文件来源
- 后续替换任意运行时或执行器时，核心记忆不受影响

## 当前阶段对这部分的结论

截至当前阶段，更合理的高层判断如下：

- 目录结构必须先服务于边界清晰，而不是先服务于搜索方便
- 顶层至少应区分 `global/`、`projects/`、`matters/`、`inbox/`
- 项目和事务目录都应采用固定骨架
- 文档类型与目录层级必须明确分离
- 自动提取内容必须先进入候选层，再进入正式层
- 这部分一旦稳定，后续再接 `Mem0`、`OmniAgent`、`SQLite` 或向量层都会容易很多

## 对当前设计的实用性与可维护性评估

到当前为止，这套设计整体方向是合理的，但如果不主动收束，后续确实有变复杂、变乱、难维护的风险。

当前最需要正视的问题不是“能力够不够多”，而是：

- 目录是否会越分越细
- 文档类型是否会越加越多
- 自动提取是否会制造大量候选噪声
- 项目、事务、会话、全局之间是否会逐渐混线

如果这些问题不提前用原则压住，后面就很容易出现下面几种失败形态：

- 结构上看起来完整，但实际没人愿意维护
- 候选内容太多，正式归档越来越少
- 目录层次过深，查找和回顾反而困难
- 自动提取越来越多，但高价值记忆越来越不清晰

因此，当前需要正式引入一条更高优先级的记忆管理原则。

## 当前最推荐的最高记忆管理原则

当前最推荐的最高原则可以表述为：

**记忆系统的第一目标不是“尽可能多地记住”，而是“用最小必要复杂度，长期稳定保存对未来风险判断真正有价值的内容”。**

这条原则建议作为后续所有设计调整的最高判断基线。

它包含四个同时成立的要求：

### 1. 价值优先

只有真正服务未来风险判断、纠偏、回顾、重构的内容，才值得进入正式记忆层。

### 2. 简洁优先

如果两个方案都能表达同样的记忆价值，应优先选择更简单、更易维护的方案。

### 3. 边界优先

宁可少一点自动化，也不能让项目、事务、会话、全局之间的边界逐渐混乱。

### 4. 长期可维护优先

任何短期方便但会让未来回顾、纠偏、迁移变难的做法，都不应进入核心层。

## 用这条原则反看当前设计

如果用这条最高原则回看当前设计，整体上是成立的，但还应继续收束成“少数稳定结构”，而不是继续加层。

### 当前设计中合理的部分

以下部分当前看是合理的，应当保留：

- `Markdown + Git` 作为唯一真相源
- `global/`、`projects/`、`matters/`、`inbox/` 四个顶层分区
- 正式层与候选层分离
- 会话作为提取来源和监督入口
- 监督系统附着在原生会话上，而不是重造主会话

这些部分虽然不算极简，但结构上是清楚的，而且长期维护成本可控。

### 当前设计中需要警惕的部分

以下部分最容易在后续演进中失控：

- 文档类型不断增加
- 项目目录和事务目录越来越深
- 会话级候选文件大量堆积
- 快捷入口与完整面板不断塞入新功能
- 自动提取候选越来越多，但确认机制跟不上

这些地方如果不提前约束，后面最容易变成“功能看似很全，实际上没人能持续维护”的状态。

## 当前建议的收束方向

为了保证简洁、清晰、可维护，当前建议主动做以下收束。

### 1. 顶层目录不再继续扩张

当前建议把顶层长期稳定控制在：

- `global/`
- `projects/`
- `matters/`
- `inbox/`

除非后面出现明确无法表达的新边界，否则不要轻易再新增新的顶层分类。

### 2. 正式文档类型控制在少数固定类别

当前建议正式文档类型长期控制在：

- 基线
- 增量
- 决策
- 评估
- 证据
- 经验

后续即使出现新场景，也优先尝试映射到这几类，而不是动不动新增一种文档类型。

## 文档类型应当克制，标签承担主要扩展性

这里需要进一步明确一条重要收束原则：

**文档类型只负责表达少数稳定结构，真正的灵活扩展能力应尽量交给标签，而不是继续增加文档类型。**

这条原则很重要，因为一旦文档类型开始泛滥，后续最容易出现以下问题：

- 用户无法快速判断一份内容到底该归到哪一类
- 自动提取系统很难稳定分类
- 后续回顾时需要先理解类型体系本身
- 目录和类型一起膨胀，维护成本迅速上升

因此，当前更推荐的方向不是：

- 不断新增“更精确”的文档类型

而是：

- 保持少数稳定正式类型
- 允许每一份文档带多个标签
- 通过标签表达更细粒度语义

## 标签的定位

当前更合理的判断是：

标签应当承担下面这些职责：

- 表达主题
- 表达风险类型
- 表达技术方向
- 表达阶段状态
- 表达适用范围
- 表达经验特征

也就是说：

- 文档类型回答“这份东西在结构上属于什么”
- 标签回答“这份东西具体和哪些语义相关”

这两个维度不能混淆。

### 标签、分类与权重的分工

为了避免后续把治理做重，当前建议再明确三者分工：

- 标签可以很多，也允许人工编辑和修订，不必每次都人工确认
- 分类数量必须少，且正式落档前必须人工确认
- 权重用于表达一条记忆对项目的约束强度，尤其是原始需求、场景需求、成功标准、关键决策这类高权重内容，建议人工确认

也就是说：

- 标签负责语义扩展
- 分类负责结构落位
- 权重负责重要度和约束力

这三者不能互相替代。

## 当前最推荐的类型数量控制

如果继续坚持“最小必要复杂度”，当前更推荐把正式文档类型长期压在极少数类别之内。

甚至第一阶段完全可以只固定四类：

- 基线
- 增量
- 决策
- 评估

然后通过标签去表达下面这些更细的语义：

- 风险
- 测试
- 重构
- 审阅
- 完成度
- 偏离
- 约束
- 成功标准
- 非目标
- 候选
- 已确认

这样会比不断新增正式文档类型更稳。

## 标签应允许多值并存

当前建议明确：

**每一份文档都应允许存在任意多个标签。**

这是合理的，因为高价值记忆往往天然跨多个维度。

例如一份文档可能同时具有：

- `risk`
- `refactor`
- `constraint`
- `high-priority`
- `reasonix`

如果标签被限制得太死，后续反而需要新增更多文档类型去补偿，这会违背当前的收束原则。

## 标签不一致问题的判断

你提到一个非常现实的问题：

- 语义相同，但提取出来的标签词汇不同

例如：

- `review`
- `code-review`
- `审阅`
- `代码审阅`

当前更合理的判断是：

- 标签一致性很重要
- 但第一阶段不必为了标签统一而把体系做得很重

因此，当前建议的优先级应当是：

### 第一优先级

- 先允许标签存在一定不一致
- 只要语义检索能够稳定命中，就暂时可以接受

### 第二优先级

- 当标签噪声已经明显影响检索和回顾时
- 再引入标签整理或标签映射机制

这比一开始就设计一整套复杂标签治理系统更符合你的目标。

## 当前对标签整理的建议

标签整理应当被视为：

- 有价值
- 但不是第一阶段最高优先级

更准确地说：

- 标签规范化可以后做
- 标签别名映射可以后做
- 标签语义合并可以后做

前提是：

- 当前检索质量没有明显受损
- 当前回顾和提炼没有明显受阻

这符合你说的那一点：

- 如果同样语义可以稳定搜索得到，那么暂时不整理也完全可以接受

## 当前最推荐的标签策略

如果要把这部分压成最容易执行的策略，当前最推荐的是：

- 类型尽量少
- 标签尽量多值
- 标签允许暂时不完全统一
- 真正影响检索和回顾时再整理

这条策略兼顾了：

- 简洁
- 灵活
- 可维护

## 下一阶段：标签体系最小治理

既然文档类型已经被收束到少数稳定类别，下一步最值得推进的就是“标签体系最小治理”。

这里的目标不是建立一个复杂词表，而是让标签既能自由扩展，又不至于完全失控。

## 标签体系的基本判断

当前更合理的判断是：

**标签是高价值记忆的主要扩展接口，但标签本身不应演化成第二套复杂分类系统。**

这意味着：

- 标签应当比文档类型更灵活
- 标签应当允许多值
- 标签应当允许一定程度的同义词并存
- 标签不应要求一开始就绝对统一

如果把标签做得过重，它就会反过来变成新的维护负担。

## 标签体系的最小目标

当前建议标签体系第一阶段只承担四个目标。

### 1. 快速表达语义

用少量标签快速表达一份文档最重要的语义特征。

### 2. 支持搜索命中

让后续无论是人工浏览还是自动检索，都能通过标签快速缩小范围。

### 3. 支持回顾过滤

让用户在回顾历史时，可以通过标签快速定位：

- 风险类内容
- 重构类内容
- 审阅类内容
- 测试类内容
- 纠偏类内容

### 4. 支持后续逐步治理

当某些标签明显重复、明显冲突、明显影响检索时，再逐步整理。

## 标签的最小使用原则

当前建议标签使用遵循以下原则。

### 1. 多而不乱

允许一个文档有多个标签，但不要为了凑标签而打无意义标签。

### 2. 语义优先

标签优先表达语义，不优先表达结构。

结构信息已经由目录和文档类型承担了。

### 3. 先用后治

先允许标签自然生长。

只有在它们真正影响使用时，再做治理。

### 4. 搜索优先于命名洁癖

如果两个标签语义接近，但实际搜索和回顾没有问题，就不必为了形式统一过早整理。

这与你的目标一致：

- 能搜到就先不折腾
- 真正需要统一时再统一

## 标签的建议约束

虽然标签要灵活，但也不能完全放飞。

当前建议至少保留下面几个约束。

### 1. 标签必须可追溯

每个标签最好能知道它是：

- 用户手工加的
- 监督系统建议的
- 自动提取的

这样后续如果发现某类标签质量差，才知道该修哪一层。

### 2. 标签必须可回填

监督系统建议的标签应当允许用户确认后再正式进入记忆层。

### 3. 标签必须可别名映射

如果某个语义出现多个常见写法，后续可以逐步建立别名关系。

但这里强调：

- 这是后续治理项
- 不是第一阶段硬性前置项

### 4. 标签必须支持宽松容错

如果一条文档带了几个近义标签，而搜索仍然能稳定命中，那么这不算问题。

## 当前建议的标签来源

为了让标签既有用又不失控，当前建议标签来源分成三类。

### 1. 人工标签

由用户直接确认或手工添加。

优先级最高。

### 2. 监督系统建议标签

由监督系统在提取和评估时生成候选标签，再由用户确认。

这是第一阶段最重要的标签来源之一。

这类标签可以先进入候选状态，后续允许用户直接人工编辑，不必要求每次都做逐条确认。

### 3. 自动推断标签

由系统根据内容自动推断。

这类标签最容易产生噪声，因此：

- 可以生成
- 但不应默认直接升格为正式标签

## 当前建议的标签分类思路

如果暂时还是需要一点点分类感，当前建议只用“弱分类”，而不要用“强分类”。

也就是说，标签可以大致落在这些方向：

- 风险
- 目标
- 约束
- 场景
- 经验
- 决策
- 状态

但不要把这些方向做成一套复杂树状体系。

它们更适合作为“语义族群”，而不是严格层级。

## 当前不建议做的标签治理

为了保持简洁，当前不建议一开始就做以下事情：

- 强制统一全部同义标签
- 强制建立复杂标签树
- 强制建立层级标签命名规范
- 强制把所有旧标签全部清洗一遍

这些事情未来都可能有价值，但不适合第一阶段。

## 当前建议的标签治理节奏

最合理的节奏应当是：

1. 先允许标签自然使用
2. 先依靠搜索能力观察是否真正够用
3. 只有在检索、回顾、提炼受影响时再整理
4. 优先整理高频、明显重复、明显影响回顾的标签

这样做的好处是：

- 不会过早把系统做重
- 不会把标签治理变成一项独立大工程
- 能让真实使用决定治理优先级

## 当前推荐的标签治理原则总结

如果把标签体系收束成一句话，当前最推荐的原则是：

**标签要足够自由以便快速表达语义，也要足够克制以便长期维护。**

## 当前设计因此应做的进一步收束

基于这条原则，当前建议再做两条收束。

### 1. 暂不继续增加正式文档类型

除非出现明确无法映射的内容类型，否则当前不再新增新的正式文档类型。

### 2. 把更多细粒度语义交给标签

后续如果出现：

- 风险子类
- 技术主题
- 经验主题
- 阶段状态
- 平台指向

优先放进标签，而不是优先变成新目录或新文档类型。

### 3. 候选内容必须有淘汰机制

`inbox/` 和 `sessions/` 中的候选内容不能只进不出。

当前原则上应当只允许三种去向：

- 升级为正式记忆
- 提炼为全局经验
- 归档或放弃

如果没有这条淘汰机制，候选层最终一定会失控。

### 4. 自动提取默认从严

当前建议默认立场应当是：

- 少提取
- 只提取高价值内容
- 先候选
- 后确认

而不是：

- 广泛提取
- 事后慢慢整理

因为后者几乎一定会制造维护灾难。

### 5. 监督入口功能默认从少

浮动入口、快捷区、完整面板的功能都应当从少开始。

第一阶段真正必须稳定的功能其实只有：

- 触发提取
- 触发评估
- 查看候选回复
- 回填输入框
- 确认归档

如果一开始塞入太多状态和动作，界面会比记忆层更早失控。

## 当前最推荐的维护策略

如果要让这套系统长期可维护，当前最推荐的策略不是“先设计得尽量完整”，而是：

- 先定义少数硬原则
- 先固定少数稳定结构
- 后续所有新增能力都必须先通过这套原则审查

因此，当前建议明确一条后续修正规则：

**任何新的目录、文档类型、自动提取规则、监督入口动作，如果不能明显提升未来风险判断质量，就不应进入核心设计。**

这条规则比“先做上去，以后再整理”更适合你现在这个项目。

## 当前阶段的最终判断

综合来看，当前这套设计：

- 方向是合理的
- 结构已经接近可推进
- 但必须以“最小必要复杂度”持续收束

如果要用一句话概括当前最推荐的记忆管理总原则，那么就是：

**宁可少记、少分、少自动化，也不要为了短期方便破坏长期清晰度、可回顾性和可维护性。**

这条原则建议正式作为后续所有设计改动的最高约束。

## 最小可行记忆体系

如果要进一步确保这套设计足够实用、足够简洁，当前建议再收束出一个“最小可行记忆体系”。

它的目标不是覆盖所有未来能力，而是先保证：

- 结构不乱
- 可以真实使用
- 后续容易维护
- 后续容易扩展

## 最小可行版本应当只保留哪些东西

当前最推荐的最小可行版本，可以只保留下面这些结构。

### 顶层目录

只保留：

- `global/`
- `projects/`
- `matters/`
- `inbox/`

这已经足够表达当前最重要的边界。

### 正式文档类型

第一阶段甚至可以先只强制使用四类正式文档：

- 基线
- 增量
- 决策
- 评估

其中：

- 证据可以先作为评估文档的附属部分存在
- 经验可以先集中进入 `global/`，不急着再细分

这样会比一开始就完整铺开六类文档更容易维护。

### 候选层

候选层只保留一个原则：

- 所有自动提取内容先进入 `inbox/` 或会话候选区

不要一开始再细分太多候选类别。

### 会话侧记录

会话侧第一阶段只需要保留：

- 会话标识
- 工作区锚点
- 最近一次提取结果
- 最近一次评估结果
- 最近一次候选回复

这已经足够支撑缓存命中和监督连续性。

## 最小可行版本下的推荐项目骨架

如果进一步压缩，单个项目目录第一阶段甚至可以先收束为：

```text
projects/
  <project-slug>/
    README.md
    baseline/
    increments/
    decisions/
    evaluations/
    matters/
```

下面这些目录都可以作为第二阶段再加：

- `evidence/`
- `sessions/`
- `archives/`

不是说它们不重要，而是：

- 第一阶段先不强制出现
- 只有在真实使用中发现确实需要时再补

这样更符合“最小必要复杂度”原则。

## 最小可行版本下的推荐事务骨架

同理，事务目录也可以先压缩为：

```text
matters/
  <matter-slug>/
    README.md
    baseline/
    increments/
    decisions/
    evaluations/
```

这已经足够支持：

- 一次纠偏
- 一次重构
- 一次评估
- 一次项目外重要事务

## 当前最推荐的归档节奏

为了防止后期失控，当前建议第一阶段把归档节奏也尽量做简单。

最推荐的顺序是：

1. 原生会话继续推进
2. 监督系统提取候选内容
3. 候选内容进入 `inbox/`
4. 用户确认后进入正式目录
5. 长期复用价值明确后再提升到 `global/`

这个节奏的好处是：

- 不会直接污染正式层
- 不会过早提炼全局经验
- 便于用户实际使用时逐步校正提取质量

## 当前最不建议过早做的事情

如果目标是实用又简洁，当前最不建议过早做的是：

- 一开始就把证据体系做得很重
- 一开始就做复杂的 `sessions/` 目录层级
- 一开始就把全局经验分很多子类
- 一开始就把每种候选内容拆成很多目录
- 一开始就做全自动正式归档

这些事情未来都可能需要，但现在过早做，只会增加维护负担。

## 当前最推荐的简化判断

如果要用最简洁的话概括当前的第一阶段结构，建议理解为：

- `projects/` 和 `matters/` 负责正式记忆
- `global/` 负责复用经验
- `inbox/` 负责缓冲候选
- 原生会话负责产生输入
- 监督系统负责提取、评估、候选回复和回填

如果这五点能稳定成立，第一阶段就已经足够可用了。

## 当前对简洁性的最终建议

所以，当前最推荐的不是继续增加更多分类，而是：

- 保留已经明确的核心边界
- 尽量推迟细节分化
- 让真实使用暴露出哪些地方真的需要再加结构

这会比“先设计得很全”更符合你的目标。

## 当前建议立即固定的设计决策

如果目标是避免后续越做越乱，那么当前建议先把下面这些决策固定下来，不要再轻易摇摆。

### 1. 真相源固定

立即固定：

- `Markdown + Git` 是唯一真相源

这条不应再反复讨论。

### 2. 顶层边界固定

立即固定：

- `global/`
- `projects/`
- `matters/`
- `inbox/`

除非后面真的出现无法表达的新边界，否则不再新增顶层目录。

### 3. 正式层与候选层固定分离

立即固定：

- 自动提取结果不能直接进入正式层
- 必须先经过候选层

这条是防止系统后续失控的关键约束之一。

### 4. 原生会话与监督系统角色固定分离

立即固定：

- `Reasonix` / `OpenCode` 保持原生会话所有权
- 监督系统只做附着式协作层

这条边界不应后面再模糊掉。

### 5. 手动模式优先固定

立即固定：

- 第一阶段优先做手动触发
- 托管模式放在其后

否则很容易为了自动化过早提高复杂度。

## 当前建议故意不固定的设计决策

为了避免过早锁死错误结构，下面这些内容当前建议故意不固定。

### 1. 具体元数据字段全集

现在不必定死每类文档完整字段集合。

### 2. 复杂证据体系

现在不必把证据单独做成沉重结构。

### 3. 复杂 sessions 目录层级

现在不必把会话侧归档做得很深。

### 4. 全自动正式归档规则

现在不应放开。

### 5. 全局经验的细分类法

现在不必先设计很多主题子类。

这类内容故意不固定，并不是忽略它们，而是为了保护整体简洁性。

## 当前最推荐的推进姿势

如果你现在要真的推进，而不是继续只讨论方向，那么当前最推荐的推进姿势是：

- 先固定少数硬边界
- 先让最小可行版本跑起来
- 再根据真实使用频次补充局部结构

这条姿势比“继续先想得更全一点”更适合你现在这个项目。

## 当前阶段最适合的收口结论

到这里，当前更适合收口成下面这句话：

**核心记忆系统现在已经不缺概念，缺的是一套足够克制、足够稳定、能开始真实使用的最小骨架。**

而当前文档里，最小骨架其实已经基本齐了。

## 继续下一阶段设计之前必须回答的问题

在继续进入更具体设计之前，当前必须先回答这个问题：

**这套需求记忆模型，是否已经足够准确，足以作为后续目录结构、文档模板、索引结构、监督视图和评估逻辑的共同约束基础？**

如果答案是“是”，下一步就可以进入更具体但仍然保持高层次的设计，例如：

- 记忆文档分类体系
- 目录层级与项目 / 事务分隔规则
- 记忆条目模板
- 有效性与状态流转规则

如果答案不是“是”，应当先修正这里的需求记忆模型，而不是直接进入实现细节。

## 分层拼装方案

基于当前已经评估过的几个开源项目，现阶段更合理的推进方式不是“选一个总平台一次性押注”，而是采用分层拼装。

这样做的原因很明确：

- 可以快速跑起第一版可用系统
- 可以优先借力成熟或半成熟能力
- 可以避免因为某一个项目不合适而整体推倒重来
- 可以让高优先级记忆系统始终保持独立，不被单一执行器或单一前端绑架

## 当前建议的总体分层

当前更合理的总体分层如下：

### 1. 核心层

职责：

- 原始需求保存
- 需求增量保存
- 决策记录
- 风险模式记录
- 全局记忆、项目记忆、事务记忆、会话记忆管理
- 回顾、提炼、矛盾检查
- 高优先级记忆抽离与重评估

当前判断：

- 这一层不应直接外包给现有任一开源项目
- 这一层应当由你要做的新系统自己定义和掌控

### 2. 记忆检索增强层

职责：

- 扫描 `Markdown` 记忆文档
- 切块与索引
- `SQLite` 检索
- 可选向量检索
- 运行时按问题召回相关记忆片段

当前最适合借力的对象：

- `OmniAgent`

当前判断：

- 这一层非常适合直接借力 `OmniAgent` 的记忆发现、切块、`SQLite + FTS5` 与选择性注入思路
- 但应保持为低耦合组件，服务于你的主系统，而不是反过来定义主系统

### 3. 执行与会话底层

职责：

- 与 `Codex`、`Reasonix`、`OpenCode` 等执行器交互
- 维持会话
- 保持工作区上下文
- 承载实时协作
- 暴露可监督的执行过程

当前最适合优先评估的对象：

- `Reasonix`
- `Codex`

当前判断：

- `Reasonix` 更适合作为第一优先级底座候选
- `Codex` 仍然是重要执行器，但更适合作为被保护的原生接入对象
- 这一层不宜直接用 `conductor` 替代

### 4. 交互监督层

职责：

- 显示需求视图
- 显示会话视图
- 支持即时纠偏
- 支持回顾和提炼
- 支持查看评估结果和风险状态

当前判断：

- 这一层最终应当由独立 `Web` 驾驶舱承担
- 不建议直接拿某个现成项目完整替代
- 前期可以借现有项目的 `Web UI` 或网关能力做原型，但不应把交互层永久绑定给它们

### 5. 协作归档层

职责：

- 需求讨论沉淀
- 决策沉淀
- 合并请求审阅
- 可追溯审计
- 面向团队或中长期项目协作

当前最适合借力的对象：

- `Gitea`
- `Forgejo`

当前判断：

- 它们非常适合做外层协作与审计表层
- 不适合承担核心记忆内核
- 不适合承担第一阶段实时监督中枢

### 6. 长期在线协调层

职责：

- 巡检
- 提醒
- 通知
- 异步交互
- 任务派发
- 任务运营

当前最适合借力的对象：

- `Hermes`

当前判断：

- `Hermes` 在这一层的适配度很高
- 比 `OmniAgent` 更适合承担长期在线协调中枢

### 7. 外围编排层

职责：

- 多步骤流程编排
- 任务路由
- 失败恢复
- checkpoint / resume
- 人工 gate

当前最适合借力的对象：

- `conductor`

当前判断：

- 它更适合后续作为外围流程层
- 现阶段不应让它主导核心交互或核心记忆模型

## 各项目的推荐角色

为了避免后续再反复混淆，当前可以把几个项目的推荐角色收束如下。

### `Reasonix`

推荐角色：

- 执行与会话底层优先候选
- 本地 TUI / Desktop / Web 能力底座
- 后续可扩展执行器适配面

不推荐角色：

- 需求记忆内核
- 风险导向记忆模型的直接替代品

### `Codex`

推荐角色：

- 高能力执行器
- 本地工作区深度协作执行器
- 需要被监督系统保护性接入的重要对象

不推荐角色：

- 被强行降级为普通脚本子进程
- 直接承担需求记忆与审计结构

### `Hermes`

推荐角色：

- 长期在线协调中枢
- 消息入口与提醒中心
- 巡检与异步推进层

不推荐角色：

- 需求记忆内核
- 第一阶段执行层总底座

### `OmniAgent`

推荐角色：

- 记忆检索增强层
- 经验提炼与自举辅助层
- 可选的多渠道原型层

不推荐角色：

- 总平台
- 核心需求记忆模型的直接拥有者
- 直接替代 `Reasonix` 或 `Hermes`

### `Gitea` / `Forgejo`

推荐角色：

- 协作归档层
- 讨论沉淀层
- 决策审计层
- 代码关联层

不推荐角色：

- 第一阶段实时监督驾驶舱
- 需求记忆内核

### `conductor`

推荐角色：

- 外围流程编排层
- 需要 checkpoint / resume / human gate 的工作流层

不推荐角色：

- 第一阶段主交互壳
- 核心需求记忆系统

## 如何以搭积木方式尽快跑起来

如果目标是“尽快用起来”，而不是继续停留在大方向讨论，当前更合理的最小拼装路径应当是：

### 第一阶段

- 自己定义 `Markdown + Git` 的核心记忆体系
- 用 `Reasonix` 或 `Codex` 作为执行主体
- 用独立最小 `Web` 页面承载需求视图和会话视图
- 优先借力 `sqlite-memory` 或 `Basic Memory`，先跑通“`Markdown` 真相源 + 索引检索 + 检索后选择性注入”

这一阶段的目标不是平台完整，而是先验证：

- 需求记忆是否真的能稳定约束执行
- 检索出来的记忆是否真的能帮助纠偏
- 会话监督与需求视图是否真的形成有效闭环

### 第二阶段

- 接入 `Hermes`
- 跑通通知、巡检、异步回复、任务提醒
- 把历史纠偏和经验提炼纳入回顾流程

这一阶段重点验证：

- 系统能否脱离前台长期运行
- 纠偏是否可以异步发生
- 全局经验是否开始稳定积累

### 第三阶段

- 接入 `Gitea` / `Forgejo`
- 把需求讨论、审计、代码审阅沉淀到外层协作平台
- 在需要时引入 `conductor` 做外围流程编排

这一阶段重点验证：

- 团队协作和历史归档是否变得顺畅
- 复杂流程是否确实需要编排层
- 记忆系统是否仍然保持核心独立性

## 当前最值得优先复用的能力

如果现在只能优先复用少量能力，当前优先顺序建议如下：

### 第一优先级

- `sqlite-memory` 或 `Basic Memory` 的 `Markdown + 索引 + 检索` 能力
- `Reasonix` 的执行与会话底层能力

### 第二优先级

- 自研风险导向监督服务的最小骨架
- `Hermes` 的长期在线协调和通知能力

### 第三优先级

- `OmniAgent`、`Mem0`、`Cognee` 这类经验提炼或检索增强能力
- `Gitea` / `Forgejo` 的协作归档能力
- `conductor` 的外围流程编排能力

这个排序背后的理由是：

- 先守住需求记忆和会话监督，才能避免系统从第一天就跑偏
- 先把执行与 `Markdown` 记忆后台跑通，才能验证这条路线是否真的有用
- 协作归档、长期在线、流程编排都很重要，但它们都应建立在核心约束已经成立之后

## 当前对“借力搭积木”的结论

综合来看，当前最合理的总体策略不是：

- 选一个项目完全押注

而是：

- 自己掌握核心记忆系统
- 对现有项目做分层借力
- 让每个项目只承担自己最擅长的那一层
- 通过低耦合边界逐步拼装

这条路线最符合你当前的真实目标：

- 快速跑起来
- 借力进化
- 保留纠偏能力
- 保留重构能力
- 不被任何单一开源项目绑死

## 当前建议的项目组成

基于目前已经收束后的判断，当前最合理的项目组成不应再表述为“一个大而全的平台”，而应明确拆成少数几个职责清晰的部分。

当前建议的组成如下：

### 1. `Reasonix` / `OpenCode`

系统定位：

- 原生执行器
- 原生会话层
- 工作区与任务推进承载层

适合的理由：

- 不需要重造 Coding Agent
- 可以保留你已经习惯的原生交互方式
- 后续替换执行器时，不必重做记忆底座

主要风险：

- 会话读取边界和写回边界是否稳定，仍需后续验证
- 不同执行器的接入方式未必完全一致

### 2. `Markdown` 知识库真相源

系统定位：

- 需求记忆真相源
- 高优先级风险记忆归档层
- 项目 / 事务 / 全局三类长期知识载体

适合的理由：

- 可直接阅读
- 可直接版本化
- 可脱离当前程序独立存活
- 未来即使重构或换底座，也不会丢失最重要的记忆

主要风险：

- 如果没有稳定索引层，后续检索、回顾和自动提取会越来越吃力
- 如果文档结构失控，最终会退化成难维护的文件堆

### 3. `Markdown + SQLite` 记忆后台

系统定位：

- 真相源之上的索引与检索增强层
- 候选记忆、正式记忆、标签和来源信息的快速读取层

适合的理由：

- 可以把 `Markdown` 真相源和运行时检索需求分离
- 有利于后续接入搜索、过滤、召回、向量增强
- 可以尽量复用现成开源项目，不必自己维护全部底层能力

主要风险：

- 如果选型过重，可能反过来约束上层记忆模型
- 如果把数据库当成新的真相源，会破坏前面已经确定的核心原则

### 4. 自研风险导向监督服务

系统定位：

- 风险导向提取层
- 记忆候选生成层
- 偏离、完成度、质量评估层

它负责的不是通用知识库存取，而是当前项目最关键、也最难借现成项目完整替代的部分：

- 从 agent 会话提取高价值内容
- 判断哪些内容值得进入候选区
- 判断哪些内容属于高权重
- 组织候选到正式的确认流转
- 支持后续回顾、矛盾检查和重评估

适合的理由：

- 你可以把精力集中在真正独特的能力上
- 可以把通用知识库能力外包给成熟开源项目

主要风险：

- 如果范围失控，它会重新膨胀成另一个“大平台”
- 如果自动提取过宽，候选噪声会很快失控

### 5. `MCP` 适配层

系统定位：

- 监督服务对 agent 暴露能力的接口层

这里必须明确一个边界：

`MCP` 更适合作为监督服务的一种对外接口，而不应被误当成监督服务本体。

更准确地说：

- 监督服务本体应当是独立服务
- `MCP` 只是它对 agent 暴露“搜索记忆、请求风险检查、写入候选记忆”等能力的一层接口

适合的理由：

- 能最大化兼容 `Reasonix`、`OpenCode`、`Codex` 这类生态
- 可以避免把监督能力深度耦合进某一个执行器

主要风险：

- 如果把全部逻辑都塞进 `MCP` 层，后续会被协议形态限制住

## 当前对这套项目组成的判断

综合来看，这套组合是合理的，而且比前面的大而全方向更适合落地。

更准确的判断是：

- 原生执行器层保留在 `Reasonix` / `OpenCode`
- 记忆真相源保留在 `Markdown + Git`
- 检索增强层尽量复用现成开源项目
- 真正需要自研的，只保留风险导向监督服务这一薄层

这条路线最符合“尽量借力、只自研真正欠缺的能力”这个目标。

## 记忆系统开源积木候选

在已经确认“核心记忆系统必须由自己掌握”的前提下，当前仍然很值得主动筛选一批优秀的开源记忆系统项目，作为可拼装积木使用。

这里的筛选标准不是“谁名气大”，而是：

- 是否真的适合作为记忆层积木接入
- 是否有明确的存储、检索、提炼、召回边界
- 是否适合低耦合接入
- 是否能服务你当前的风险导向需求记忆体系
- 是否许可证友好，便于后续组合和演进

当前筛选后，最值得保留的候选主要有以下几类。

## 第一梯队候选

### 1. sqlite-memory

项目地址：

- `GitHub`：<https://github.com/sqliteai/sqlite-memory>
- 网站：<https://sqlite.ai/>

当前判断：

`sqlite-memory` 是当前最值得优先评估的“Markdown 记忆后台引擎”候选，也是目前最贴近你当前需求结构的底层积木。

它的优势非常明确：

- 明确面向 `Markdown` 内容
- 明确以 `SQLite` 为底层能力载体
- 支持混合检索，也就是 `FTS5 + 向量`
- 明确把 `Markdown files as the source of truth` 作为核心思路
- 许可证为 `MIT`

它最适合纳入的部分是：

- 记忆后台引擎
- 本地索引与检索层
- `Markdown` 真相源之上的加速层

它对你当前方向的主要价值在于：

- 它不会天然抢走你的上层记忆模型定义权
- 它和“`Markdown + Git` 为真相源”的核心原则高度一致
- 它更像引擎，而不是一个试图主导全部工作流的平台
- 很适合被放在你当前设想里的“记忆后台”位置

它的主要限制在于：

- 它更像底层引擎，不像完整产品
- 你仍然需要自己定义目录结构、frontmatter 约定、候选转正式规则和高权重确认规则
- 它当前生态和成熟度仍然明显弱于更“大一体化”的平台型项目

因此更合理的使用方式应当是：

- 让它承担 `Markdown + SQLite` 记忆后台引擎
- 保留你对 `Markdown` 结构和记忆条目模板的控制权
- 在其之上只自研风险导向监督服务，而不是重做底层检索

### 2. Basic Memory

项目地址：

- `GitHub`：<https://github.com/basicmachines-co/basic-memory>
- 文档：<https://docs.basicmemory.com/>

当前判断：

`Basic Memory` 是当前最值得认真考虑的“现成知识库底座”候选，也是目前最接近开箱即用的一体化替代方案。

它的优势非常明确：

- 明确采用 file-first 架构
- 明确使用标准 `Markdown` 文件作为知识载体
- 数据库只作为 secondary index
- 自带 `MCP Server`
- 自带 `CLI Tools`
- 自带 `File Watcher`
- 已明确支持 `Codex` 等客户端接入
- 本地版和云版都围绕同一套 `Markdown` 文件工作

它最适合纳入的部分是：

- 知识库底座
- 本地文件知识库 + 索引层
- 面向 agent 的现成 `MCP` 接入口

它对你当前方向的主要价值在于：

- 已经把“Markdown 文件 + 索引数据库 + MCP + 文件监听”这条链路做得比较完整
- 你可以跳过大量通用底层开发，直接把精力集中在风险导向监督能力上
- 它比单纯索引引擎更接近一个可直接拿来接入的知识库底座

它的主要限制在于：

- 许可证为 `AGPL-3.0`
- 它自带更强的知识模型和组织方式，可能会反过来约束你自己的记忆格式设计
- 如果后续需要深度定制“高权重条目、候选转正式、风险导向状态流转”，可能需要绕开或改造它既有约定

因此当前更合理的判断是：

- 非常值得保留
- 如果目标是尽快做出可用原型，它是最接近现成底座的候选
- 如果你特别重视长期许可证边界和上层结构控制权，它应排在 `sqlite-memory` 之后，而不是之前

### 3. Mem0

项目地址：

- `GitHub`：<https://github.com/mem0ai/mem0>
- 文档：<https://docs.mem0.ai/>

当前判断：

`Mem0` 仍然值得保留，但它更适合作为“通用记忆检索增强层”候选，而不是当前最优先的 `Markdown + SQLite` 记忆后台替代。

它的优势非常明确：

- 明确把自己定义为 `AI` 的记忆层
- 支持用户、会话、agent 多层记忆
- 支持自托管服务与库方式接入
- 提供多种向量存储后端
- 支持 `CLI`、SDK、服务化、自托管
- 许可证为 `Apache-2.0`

它最适合纳入的部分是：

- 记忆检索增强层
- 运行时记忆召回层
- 面向执行器的统一记忆接口层

它对你当前方向的主要价值在于：

- 可以较快跑通“记忆写入、记忆检索、相关记忆召回”这条链路
- 适合以侧车或独立服务方式接入
- 许可证友好，适合长期拼装

它的主要限制在于：

- 它更像通用记忆层，不天然等于你的风险导向需求记忆模型
- 它默认更倾向让系统把记忆写入自己的记忆结构，而不是直接围绕你的 `Markdown + Git` 真相源组织全部结构

因此更合理的使用方式应当是：

- 不让它拥有最高级别的原始需求真相源
- 让它服务于你的文档型记忆系统
- 重点借力它的召回、搜索、接口能力

### 4. Graphiti

项目地址：

- `GitHub`：<https://github.com/getzep/graphiti>
- 论文：<https://arxiv.org/abs/2501.13956>

当前判断：

`Graphiti` 仍然是当前最值得关注的“时间感知记忆图谱引擎”。

它的核心价值不是普通向量检索，而是：

- 时间有效性
- 事实随时间演化
- provenance，也就是来源可追溯
- 图结构关系检索
- 混合检索

这和你当前特别重视的几个点高度相关：

- 高优先级记忆不能静默覆盖
- 历史纠偏需要可追溯
- 系统需要支持回顾和矛盾检查
- 系统需要知道“现在生效的是哪一版要求”

它最适合纳入的部分是：

- 风险与事实关系层
- 需求增量之间的时间关系层
- 高价值记忆的结构化关联层

它的主要限制在于：

- 它更重
- 更偏图谱引擎
- 通常需要 `Neo4j` 或图数据库配套
- 对第一阶段“尽快跑起来”来说偏重

因此当前更合理的判断是：

- 非常值得保留
- 很适合作为第二阶段或第三阶段增强层
- 不建议作为第一阶段最小可用系统的首个落地积木

### 3. Cognee

项目地址：

- `GitHub`：<https://github.com/topoteretes/cognee>
- 文档：<https://docs.cognee.ai/>

当前判断：

`Cognee` 是一个很强的“知识图谱 + 向量检索 + 代理记忆平台”候选。

它值得关注的原因包括：

- 提供 `remember / recall / forget / improve` 这类比较完整的记忆接口
- 自带会话记忆与长期记忆思路
- 强调知识图谱和长期上下文
- 有 `MCP`、本地 UI、数据库适配和插件生态方向
- 许可证为 `Apache-2.0`

它最适合纳入的部分是：

- 经验提炼与长期记忆实验层
- 图谱增强的记忆检索层
- 可选的本地记忆平台原型层

它的主要限制在于：

- 整体能力面较大
- 自己就很像一个记忆平台
- 如果直接整体引入，容易和你自己的核心记忆系统边界冲突

因此更合理的纳入方式是：

- 按模块借力
- 借它的 remember / recall / improve 思路和相关实现
- 重点用于实验“经验提炼、长期记忆、全局记忆”这一层

## 第二梯队候选

### 4. Letta

项目地址：

- `GitHub`：<https://github.com/letta-ai/letta>
- 文档：<https://docs.letta.com/>

当前判断：

`Letta` 很强，但它更像“带高级记忆能力的 stateful agent 平台”，而不是单纯的记忆积木。

它的价值主要在于：

- 长状态 agent
- memory blocks
- stateful agents API
- 本地 CLI 与应用集成能力

它的主要问题是：

- 更容易把你带向“以 Letta 为中心搭平台”
- 而不是“把它作为记忆层积木接入”

对于你当前方向来说，这会带来两个风险：

- 抢走 `Reasonix` / `Codex` 的执行层位置
- 抢走你自己的需求记忆系统边界

因此当前判断是：

- 值得了解
- 但不适合作为第一优先级记忆积木
- 更适合作为“对照参考对象”，或者未来某个专门状态 agent 场景的备用底座

## 明确不建议优先采用的候选

### OpenMemory

项目地址：

- `GitHub`：<https://github.com/mem0ai/mem0/tree/main/openmemory>

当前判断：

`OpenMemory` 现在不建议单独作为重点候选。

原因很简单：

- 它已经公开标注为正在 sunset
- 官方也建议转向 `Mem0` 自托管服务

因此它现在最多只适合作为历史参考，不适合作为新的重点拼装对象。

## 当前推荐优先级

如果从“最适合拿来作为积木”的角度排序，当前建议顺序如下：

### 第一优先级

- `sqlite-memory`

理由：

- 最符合“`Markdown + Git` 为真相源，`SQLite` 为增强层”的核心原则
- 更像底层引擎，不会过早抢走你的上层结构控制权
- `MIT` 许可证更适合长期低耦合拼装
- 最适合承担你当前组合里的“记忆后台”位置

### 第二优先级

- `Basic Memory`

理由：

- 最接近现成可用的知识库底座
- 已经把 `Markdown`、索引数据库、`MCP`、文件监听组合在一起
- 很适合快速验证原型
- 但 `AGPL-3.0` 和它自带的知识模型约束，需要单独审慎评估

### 第三优先级

- `Mem0`

理由：

- 适合承担通用记忆召回和检索增强
- 但不如前两者贴近“`Markdown + SQLite` 记忆后台”这个问题本身

### 第四优先级

- `Graphiti`

理由：

- 长期价值很高
- 但对第一阶段落地来说仍然偏重

### 第五优先级

- `Cognee`

理由：

- 能力面很强
- 很适合做长期记忆和经验提炼实验
- 但平台感较强，需要控制边界

### 第六优先级

- `Letta`

理由：

- 很优秀
- 但更像另一套 stateful agent 平台
- 和你当前“保留 `Reasonix` / `Codex` 执行层”的方向不够一致

## 当前最推荐的纳入方式

如果目标是“尽量用优秀开源项目做积木”，当前最推荐的纳入方式不是把这些项目全部并进来，而是分工使用。

### 方案一

- 用你的系统掌握 `Markdown + Git` 真相源
- 用 `sqlite-memory` 承担第一版 `Markdown + SQLite` 记忆后台
- 用 `Reasonix` / `Codex` 承担执行与会话

这是当前最现实、最稳的一条路线。

### 方案二

- 在方案一基础上
- 如果需要更快做原型，可以改用 `Basic Memory` 承担知识库底座
- 重点验证“现成底座 + 自研风险监督薄层”是否足够顺手

这条路线更适合快速验证，但要单独评估许可证和结构控制权。

### 方案三

- 在方案一基础上
- 让 `Graphiti` 进入第二阶段
- 专门承担时间关系、事实演化、来源追溯、矛盾检查

这条路线更贴近你长期目标，但不适合一开始就全量压上。

### 方案四

- 把 `Mem0` 或 `Cognee` 作为经验提炼和长期记忆实验支线
- 用来验证“全局经验记忆”“remember / recall / improve”“session 到长期记忆蒸馏”是否值得吸收

这条路线适合并行研究，不适合作为第一阶段唯一主线。

## 当前结论

综合判断如下：

- 当前确实存在值得作为积木使用的优秀开源记忆系统项目
- 其中最值得优先纳入的是 `sqlite-memory`
- 最适合作为现成知识库底座快速验证的是 `Basic Memory`
- `Mem0` 更适合作为通用记忆检索增强层候选
- 最值得为长期结构保留的是 `Graphiti`
- 最值得作为实验性增强平台关注的是 `Cognee`
- `Letta` 更适合作为参考和备用方向，而不是当前主线积木
- `OpenMemory` 不建议再作为新项目重点投入对象

这意味着下一步如果你要继续推进，已经可以从“核心记忆系统自己掌握”切换到“挑一到两个记忆层积木做最小接入验证”的阶段了。

## 下一阶段：单条记忆条目模板

既然当前已经收束到“记忆条目”才是最小对象，那么下一步最需要固定的，不是数据库表结构，而是：

- 一条正式记忆最少要包含什么
- 哪些字段必须稳定
- 哪些字段可以后续再补

这一层的目标必须继续保持克制。

也就是说：

- 要足够清晰，能支撑后续评估、检索、回顾和重评估
- 但不要一开始就做成沉重 schema

## 单条记忆条目的最小目标

当前建议，一条正式记忆条目至少要同时回答下面几个问题：

- 这条记忆是什么
- 它属于哪里
- 它有多重要
- 它当前是否生效
- 它从哪里来
- 它和哪些内容有关

如果连这几个问题都回答不了，那么后续再做检索、评估、回顾时就一定会混乱。

## 当前最推荐的最小字段集

当前最推荐先固定下面这些最小字段。

### 1. `id`

作用：

- 作为稳定标识
- 用于关系引用
- 用于后续替代、修正、支撑、提炼等关联

要求：

- 稳定
- 唯一
- 不依赖标题本身

### 2. `title`

作用：

- 供人快速阅读
- 供目录浏览和回顾时快速识别

要求：

- 尽量短
- 直接表达当前记忆的核心意思

### 3. `type`

作用：

- 表示这条记忆在正式结构上属于哪一类

当前第一阶段建议只允许落在少数稳定类型中，例如：

- `baseline`
- `increment`
- `decision`
- `evaluation`

这里的 `type` 应当和前面已经确定的正式文档类型保持一致，不要再单独发明一套新类型。

### 4. `scope`

作用：

- 表示这条记忆属于哪一层作用域

当前建议作用域只允许：

- `global`
- `project`
- `matter`
- `session`

这条字段直接决定后续：

- 该记忆会被谁检索到
- 它能否跨项目复用
- 它应挂在哪一层目录下

### 5. `anchor`

作用：

- 指明这条记忆具体归属到哪个对象

例如：

- 某个项目
- 某个事务
- 某个原生会话

这里不要求一开始就拆很多字段。

第一阶段更适合先用一个清晰锚点字段表达，例如：

- `project: agent-cockpit`
- `matter: refactor-review-loop`
- `session: reasonix/<session-id>`

后续如果真实使用中确实需要，再拆成更细字段。

### 6. `weight`

作用：

- 表示这条记忆对后续判断的约束强度

当前建议第一阶段直接与前面已经确定的优先级分层保持一致：

- `P0`
- `P1`
- `P2`
- `P3`

其中：

- `P0` 和 `P1` 默认视为高权重
- `P2` 和 `P3` 默认视为较低权重

当前建议规则是：

- 高权重条目正式落档前应人工确认
- 低权重条目可以更宽松，但不能自动覆盖高权重条目

### 7. `status`

作用：

- 表示这条记忆当前所处状态

当前建议第一阶段只保留少数稳定状态：

- `candidate`
- `active`
- `superseded`
- `archived`
- `rejected`

这几个状态已经足够表达：

- 候选
- 当前生效
- 已被替代
- 保留归档
- 放弃不用

没有必要一开始做更复杂的状态机。

### 8. `tags`

作用：

- 表达细粒度语义
- 支持检索和回顾过滤

这里继续沿用前面已经确定的原则：

- 标签允许多值
- 标签允许人工编辑
- 标签不必每次都人工确认
- 标签可以先不完全统一

### 9. `sources`

作用：

- 记录这条记忆是从哪里来的

至少应当能追溯到：

- 哪次用户输入
- 哪次 agent 输出
- 哪次人工整理
- 哪份历史文档

这条字段非常关键，因为没有来源，就很难回顾“为什么会有这条记忆”。

### 10. `body`

作用：

- 保存这条记忆真正要表达的内容

这里必须明确：

- 对高权重记忆，不应只保留一句摘要
- 应保留足够完整的原文或准原文表达

尤其是：

- 原始需求
- 场景需求
- 成功标准
- 关键纠偏
- 关键决策理由

不能只剩一句被过度压缩后的机器摘要。

### 11. `relations`

作用：

- 表示这条记忆与其他记忆的关系

第一阶段不必做复杂图结构，但建议至少允许下面这些关系：

- `derived_from`
- `updates`
- `supersedes`
- `supports`
- `related_to`
- `promoted_to`

这样后续就能逐步支撑：

- 增量修正
- 决策支撑
- 经验提炼
- 高优先级记忆重评估

## 当前不建议一开始强制加入的字段

为了保持最小必要复杂度，当前不建议一开始就强制要求下面这些字段：

- 复杂评分
- 复杂置信度
- 复杂生命周期时间线
- 复杂审批流记录
- 复杂向量索引参数
- 复杂展示配置

这些内容未来都可能有价值，但当前阶段会明显把模板做重。

## 单条正式记忆的最小模板建议

如果把上面的最小字段集落成 `Markdown`，当前更推荐的形态是：

```md
---
id: mem-project-agent-cockpit-0001
title: 原始目标是以需求记忆和持续纠偏为核心
type: baseline
scope: project
anchor: project:agent-cockpit
weight: P0
status: active
tags:
  - requirement
  - original-requirement
  - risk
  - supervision
sources:
  - kind: user-message
    ref: session:reasonix/abc123#msg-001
relations: []
---

## 内容

系统的核心目标不是再造一个新的 Coding Agent，而是围绕现有执行器建立需求记忆、持续监督和纠偏能力。

## 说明

这是项目级原始需求基线，后续增量可以修正解释，但不能静默改写或直接覆盖。
```

这个模板的重点不是字段多，而是回答清楚：

- 结构类型
- 归属范围
- 约束强度
- 当前状态
- 来源
- 正文

这已经足够支撑第一阶段。

## 候选记忆条目应比正式条目更轻

候选条目不应和正式条目完全一样重。

当前建议候选条目只强制要求：

- `id`
- `title`
- `type`
- `scope`
- `anchor`
- `weight`
- `status: candidate`
- `sources`
- `body`

而下面这些内容可以后补：

- 完整标签整理
- 完整关系补充
- 更精确的状态调整

这样更符合前面已经确认的节奏：

- 先候选
- 后确认
- 再正式落档

## 分类、标签、权重在模板中的边界

为了避免后续再次混淆，当前建议在模板层就把三者边界固定下来。

### 分类

这里主要由 `type` 承担。

要求：

- 数量少
- 结构稳定
- 正式落档前人工确认

### 标签

这里主要由 `tags` 承担。

要求：

- 语义扩展
- 允许多值
- 允许人工编辑
- 不要求每次逐条确认

### 权重

这里主要由 `weight` 承担。

要求：

- 直接表达约束强度
- 高权重条目优先人工确认
- 不能被低权重条目悄悄覆盖

## 正式条目与正式文档的关系

这里还需要明确一个边界：

- “记忆条目”是最小对象
- “正式文档”是条目的承载容器

也就是说，第一阶段并不一定要求一条条目对应一整个独立大文档。

更现实的做法是：

- 高权重内容可以单独成文
- 同一主题下的低权重增量也可以按批次归入同一文档

但无论承载方式如何变化，条目层都应保持可识别、可引用、可追溯。

## 当前阶段对模板设计的结论

综合来看，当前最合理的模板方向是：

- 字段少而稳定
- 优先保证来源、分类、权重、状态、正文清楚
- 标签承担主要扩展性
- 高权重内容保留更完整原文
- 候选条目比正式条目更轻

如果后续继续推进，下一步最适合进入的就不再是继续扩分类，而是：

- 条目状态流转规则
- 候选到正式的确认边界
- 高权重条目的人工确认规则
- 项目 / 事务 / 会话锚点的最小命名规则

## 再收束后的阶段判断

在前面所有讨论基础上，当前还可以再做一次更激进但更实用的收束：

**第一阶段真正必须先做的，可能不是完整监督系统，而是一个风险导向的 Markdown 知识库底座。**

这个判断的意义是：

- 先把唯一真相源立稳
- 先把原始需求、纠偏、决策、评估放到清晰结构里
- 先保证未来任何时候都能抽出高价值记忆重新评估

如果这一层没有先做好，那么后续无论是会话提取、检索增强还是监督回复，都很容易建立在不稳定基础之上。

## 这里说的“知识库底座”不等于普通笔记系统

这里说的知识库，不是普通意义上的：

- 随手记笔记
- 做文档收藏
- 只支持全文搜索

更准确地说，它应当是：

**一个以 Markdown 为真相源、以风险导向记忆为核心、支持分类、标签、权重、状态和来源追溯的知识库底座。**

它至少要能稳定承载：

- 原始需求
- 场景需求
- 成功标准
- 非目标
- 高优先级纠偏
- 技术决策及其理由
- 阶段性评估
- 可复用经验

## 为什么先做知识库底座是合理的

如果把当前目标拆开看，真正最不可替代、最不能借现成执行器直接解决的部分，其实就是：

- 什么值得长期保存
- 保存到什么结构里
- 哪些内容优先级最高
- 哪些内容当前仍然生效
- 哪些内容在未来重构时必须先被重新拿出来看

这些问题本质上都属于知识库底座问题，而不属于执行器会话问题。

因此，先把这层做稳，有几个直接好处：

- 可以先脱离具体执行器验证记忆模型是否成立
- 可以先把项目风险守住
- 可以显著降低第一阶段复杂度
- 即使后面换掉 `Reasonix`、`OpenCode`、`Codex` 接入方式，这一层也不需要重做

## 但最终目标仍然不只是知识库

虽然第一阶段可以收缩为知识库底座，但最终目标仍然不能只停留在这里。

因为你最初真正要的，还有下面两类能力：

- 从会话中自动提取高价值内容
- 在运行时基于当前需求和记忆，对原生会话做纠偏提醒或候选回复

这说明更准确的产品分层应当是：

### 第一层：知识库底座

负责：

- 保存 Markdown 真相源
- 管理分类、标签、权重、状态、来源
- 提供项目 / 事务 / 全局边界
- 支持回顾、检索、重评估

### 第二层：记忆加工层

负责：

- 从会话提取候选记忆
- 候选分类
- 候选标签建议
- 候选权重判断
- 候选转正式落档
- 检索后选择性注入

### 第三层：监督协作层

负责：

- 会话观察
- 偏离评估
- 完成度评估
- 质量评估
- 纠偏提醒
- 候选回复
- 回填原生输入框

## 这三层的推荐推进顺序

当前最稳妥的推进顺序应当明确固定为：

1. 先做知识库底座
2. 再做记忆加工层
3. 最后再做监督协作层

这个顺序的重要意义在于：

- 第一阶段先把最核心、最长期、最不该反复推倒的部分做稳
- 第二阶段再把自动化提取和检索接上
- 第三阶段才进入真正的会话监督和持续纠偏

## 如果只做一个“支持 Markdown、分类和标签的知识库”够不够

当前更准确的回答是：

- 作为第一阶段目标，够，而且很合理
- 作为最终目标，不够

因为如果只有知识库存储，而没有后续提取、检索和监督能力，那么它最终仍然更像：

- 高质量项目记忆库

而不是：

- 能持续参与执行过程的监督协作系统

所以当前最合理的定性应当是：

**先把它当作风险导向知识库底座来做，但不要误以为最终产品只需要一个知识库。**

## 当前方向因此应当如何重新表述

基于这次收束，当前方向更适合被重新表述为：

**第一期做风险导向的 Markdown 知识库底座，后续在其之上逐步增加记忆提取、检索增强和会话监督能力。**

这比直接说“先做监督驾驶舱”更稳，也更接近当前最真实的可执行路径。

## 当前阶段新的收口结论

如果现在必须进一步压缩成一句可执行结论，那么当前最合适的结论是：

**先做知识库底座，守住需求和风险记忆；监督系统是后续叠加层，不是第一步必须同时做完的东西。**

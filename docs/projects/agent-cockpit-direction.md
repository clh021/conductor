# Agent Cockpit 方向评估

## 文档目的

本文档用于整理当前阶段对产品方向的判断，供进一步评估。

本文档的目标不是进入实现细节，而是先确认以下问题：

- 这个产品真正要解决的核心问题是什么
- 它应该被定义成什么类型的系统
- 现阶段的产品方向是否正确
- 后续是否值得继续进入更具体的系统设计

## 核心问题

当前真实需求，不是下面这些任意一种单独成立的东西：

- 一个工作流编排器
- 一个新的 AI Coding Agent
- 一条代码审查流水线
- 一个简单的聊天界面

当前真实需求是一个能够围绕现有 AI Coding Agent 持续进行监督、纠偏和协作的系统。

这个系统需要同时满足以下要求：

- 保留 `codex`、`reasonix`、`opencode` 等现有工具本身的能力
- 能稳定读取并展示这些工具输出的非代码内容
- 允许用户在执行过程中随时介入
- 支持用户纠偏、改方向、补约束、补场景
- 支持连续协作，而不是仅在固定节点审批
- 后续可以扩展到编排、评审、回放、审计和自动化

因此，目标产品不应被定义为普通工作流系统，而应被定义为一个面向 AI Coding Agent 的监督与协作系统。

## 产品本质定义

当前最准确的产品定义是：

**一个以会话为中心、以需求为锚点、以纠偏为核心能力的 Agent 监督驾驶舱。**

这一定义包含四个关键点：

### 1. 以会话为中心

系统的核心对象不是单个步骤，而是一次连续执行和连续协作的会话。

### 2. 以需求为锚点

系统判断是否正确、是否完成、质量是否达标，不能只看代码结果，必须始终回到用户最初的真实需求。

### 3. 以纠偏为核心能力

系统最重要的能力不是“自动完成”，而是“允许人在过程中持续修正方向”。

### 4. 以现有 Agent 为执行主体

系统不应优先重造 `codex`、`reasonix`、`opencode` 本身，而应优先成为这些工具之上的监督层和协作层。

## 为什么 Conductor 不是核心产品形态

`conductor` 有价值，但它不是当前产品的核心形态。

`conductor` 的强项是：

- 工作流编排
- 路由与分支
- checkpoint 与 resume
- human gate
- 节点级 dialog
- 多步骤执行管理

这些能力后续可能很有帮助，但它们解决的是“流程控制”问题，不是“连续监督和纠偏”问题。

当前最优先解决的问题是：

- 如何持续保存用户真实需求
- 如何在执行过程中判断是否偏离
- 如何允许用户在过程中随时修正
- 如何保留 agent 输出、用户输入和后续判断之间的对应关系

因此，当前判断是：

- `conductor` 可以成为后续的外层流程编排组件
- `conductor` 不适合作为核心交互壳
- 第一阶段产品不应围绕 YAML workflow 展开

## 首选交互模型

当前最合理的交互模型是：

- `Web` 为主交互界面
- 必要时保留 `TUI` 作为补充
- 原生 Agent 继续作为执行主体
- 系统负责监督、展示、记忆、纠偏和记录

这个交互模型明确排除以下方向作为第一优先级：

- 把所有能力强行压缩成命令行脚本调用
- 把全部能力建立在 YAML workflow 之上
- 为了统一而牺牲原有 agent 的自然交互能力

## 为什么 Web 更适合作为主界面

将纠偏和监督会话放到 `Web` 界面中，更符合目标能力。

`Web` 的主要优势包括：

- 更适合展示长文本输出
- 更适合同时展示需求、上下文、diff、文件和操作区
- 更适合保留完整会话记录
- 更适合提供暂停、继续、回放、分叉等操作
- 更适合作为“监督驾驶舱”而不是单纯聊天框

但需要明确：

`Web` 只会降低交互层的难度，不会自动解决底层 agent 接入问题。

即使使用 `Web`，仍然必须解决以下问题：

- 如何接入不同 agent 的会话
- 如何中断与继续
- 如何统一 transcript
- 如何记录 workspace 变化
- 如何把用户纠偏反馈送回原有 agent

因此，`Web` 是正确的主交互表层，但不是全部问题的答案。

## 浏览器插件不是第一阶段基础方案

浏览器插件可以作为后续增强方式，但不适合作为第一阶段基础架构。

原因如下：

- 对第三方页面结构依赖过强
- 稳定性较差
- 很难成为权威数据源
- 难以稳定控制本地 CLI/TUI 会话
- 更适合做外挂，不适合做主系统

因此，当前更合理的基础方向是：

- 先做一个独立的 `Web` 驾驶舱
- 后续如果有必要，再考虑浏览器插件作为附加层

## 当前接近的市场方向

目前市面上存在一些相近方向的项目，但没有看到一个完全满足当前需求、并且能直接作为现成答案的成熟产品。

### OpenCode

`OpenCode` 当前看起来最接近一个适合作为实验底座的对象。

原因是它同时具备：

- Web 使用方式
- TUI 使用方式
- attach / session 类能力
- server / plugin 扩展能力

这使它更容易成为“监督层”的第一接入对象。

### Reasonix

`Reasonix` 更偏向终端使用和 agent 本体能力。

它仍然值得纳入目标接入范围，但它看起来不像一个天然适合作为监督驾驶舱底座的系统。

### Codex

`Codex` 本身能力强，但它有自己的原生生态和交互方式。

如果过早把它强行降级成脚本子进程，可能会损失它本身的优势。

因此，针对 `Codex` 更适合做“受保护的原生接入”，而不是“简单脚本调用”。

### OpenHands

`OpenHands` 更接近通用型 Web Agent 平台或控制平面。

它是一个重要参考对象，但它偏重平台化，不一定正好匹配当前这个更聚焦的监督驾驶舱目标。

## 当前方向判断

截至目前，最合理的方向判断是：

**要做的不是工作流系统，而是一个以需求记忆和持续纠偏为核心的 Agent 监督驾驶舱。**

这意味着系统的核心对象应当是：

- 需求
- 会话
- transcript
- 用户纠偏
- 决策记录
- workspace 状态
- 偏离与完成度评估

而不是只围绕：

- prompt
- 单次执行
- 脚本输出
- 节点路由

## 最高优先级原则

当前最高优先级，不是技术选型，不是架构风格，也不是二次开发方式。

当前最高优先级是：

**准确保存、解释、追踪和评估用户真实需求，尤其是与使用场景直接相关的部分。**

这是整个系统的第一原则。

因为它直接决定：

- 项目是否偏离
- 项目是否完成
- 输出质量是否达标

只有在这个前提成立后，下面这些内容才有意义：

- 技术偏好
- 架构选择
- 工具选择
- 二次开发策略
- 接入方式

## 必须把用户输入提升为一等数据

用户输入不能只被当作聊天消息保存。

系统必须把用户输入当作一等数据处理，尤其是以下类型：

- 原始需求
- 场景补充
- 约束说明
- 纠偏说明
- 拒绝说明
- 完成判断
- 质量判断
- 技术偏好

这意味着系统必须具备一个专门的“需求记忆层”。

## 需求记忆层是核心系统，而不是附属功能

这个系统不应只被看作：

- Agent 执行层

它应被看作：

- 需求记忆层
- 加上 Agent 执行层

需求记忆层负责提供：

- 方向判断依据
- 偏离判断依据
- 完成判断依据
- 质量判断依据
- 变更追踪依据
- 审计与回放依据

如果没有这一层，系统最多只是一个更好看的 Agent 聊天壳，而不是一个真正可靠的监督系统。

## 需求记忆必须有优先级分层

所有输入和记忆不能被视为同等重要。

当前建议的优先级分层如下。

### P0：任务本质层

用于保存最根本、最不可丢失的信息，包括：

- 原始需求
- 使用场景
- 用户目标
- 成功定义
- 非目标
- 边界条件

这是最高优先级层。

后续所有判断，必须首先服从这一层。

### P1：纠偏约束层

用于保存后续出现的高优先级修正，包括：

- 明确纠偏
- 防偏离约束
- 禁止事项
- 优先级变化

这一层用于修正执行方向，但不能静默抹掉 P0 原始基线。

### P2：方案偏好层

用于保存方案层面的倾向，包括：

- 技术偏好
- 架构偏好
- 工具选择偏好
- 交互偏好

这一层重要，但它不能凌驾于 P0 和 P1 之上。

### P3：实现细节层

用于保存局部实现层面的内容，包括：

- 命名建议
- refactor 想法
- 局部实现偏好
- 次级工程决策

这一层只应影响实现细节，不应反向改变任务本质。

## 原始需求必须永久保留

原始需求绝不能被系统摘要替代。

原始需求应被作为基线永久保留，并具备以下属性：

- 原文不可丢失
- 原文不可被自动总结覆盖
- 后续可以补充，但不能静默改写
- 所有后续判断都可以追溯回原文

如果存在冲突，默认规则应当是：

- 原始需求原文优先
- 除非存在明确、可追踪的后续修正

## 需求增量必须被单独记录

后续每一次纠偏、澄清、补约束，都不应只是简单追加一句消息。

这些内容应被视为“需求增量”。

需求增量应当明确指出它在修改什么，例如：

- 目标
- 场景
- 范围
- 质量标准
- 约束
- 非目标
- 技术偏好

只有这样，系统才能回答以下关键问题：

- 现在的任务要求到底是什么
- 哪些内容是后加的
- 哪些内容取代了旧约束
- 当前执行依据的到底是哪一版要求

## 必须具备分类、标签和归档能力

需求记忆系统需要分类、标签和归档功能。

这不是为了做一个“更方便搜索的笔记系统”，而是为了给后续判断提供稳定结构。

分类和标签至少要支持以下维度：

- 场景
- 目标
- 约束
- 质量要求
- 架构倾向
- 工具倾向
- 风险
- 状态
- 决策

当前建议方向是：

- 核心标签使用受控分类
- 允许附加自由标签
- 评估逻辑优先依赖受控分类

## 未来必须有两个核心视图

这个产品未来不应只有一个聊天流视图。

至少应当有两个核心视图。

### 1. 会话视图

用于：

- 看 agent 输出
- 看用户纠偏
- 继续对话
- 执行暂停、继续、分叉等操作

### 2. 需求视图

用于：

- 看原始需求基线
- 看需求增量历史
- 看当前有效约束
- 看成功标准
- 看偏离情况
- 看完成度证据

需求视图是系统避免退化成“更好看的聊天窗口”的关键。

## 核心评估逻辑必须围绕需求展开

未来所有执行结果，都应围绕三个问题持续评估。

### 1. 偏离检查

判断：

- 当前执行是否仍然符合原始需求和使用场景
- 如果偏离，偏离发生在哪一条要求上

### 2. 完成度检查

判断：

- 哪些成功标准已经满足
- 哪些部分仍然缺乏证据

### 3. 质量检查

判断：

- 即使方向没有偏离，输出质量是否足够
- 是否出现了失败信号

这三种检查必须是“需求中心”的，而不是“代码中心”的。

## 当前阶段最小方向范围

在进入更具体的设计之前，当前阶段最小应确认的方向范围应包括：

- 以会话为中心
- 以 Web 为主界面
- 保留现有 Agent
- 保存原始需求基线
- 保存需求增量
- 建立记忆分类与标签能力
- 建立偏离、完成度、质量三类评估逻辑

当前阶段不需要立即确定：

- 最终数据库结构
- 最终 API 结构
- 插件架构细节
- conductor 集成方式
- 多 agent 自动编排细节

## 当前建议的推进顺序

如果方向成立，后续推进顺序应当是：

1. 先验证“需求记忆 + 监督纠偏”是否是正确的核心
2. 先围绕一个 Agent 类型验证监督会话模型
3. 再增加更多 Agent Adapter
4. 最后再考虑 workflow、编排和自动化层

这样可以避免过早优化错误层次。

## 当前结论摘要

当前方向可以概括为以下几点：

- 目标产品不是工作流系统，而是 **Agent 监督驾驶舱**
- 它应当是 **Web 优先**
- 它应当保留 **现有 Coding Agent**
- 它的最高优先级是 **需求完整性**
- 它必须具备 **需求基线 + 需求增量 + 分类标签** 能力
- 偏离、完成度和质量，都必须回到需求视角判断
- `conductor` 更适合作为后续外围编排层，而不是第一阶段核心交互层

## 进入下一阶段之前必须回答的问题

下一阶段开始之前，必须先回答这个问题：

**当前这个方向，是否足够准确，足以支持后续围绕“需求记忆 + 持续监督 + 连续纠偏”继续做更具体的系统设计？**

如果答案是“是”，再继续下一阶段。

如果答案不是“是”，应当先修正文档中的方向判断，而不是继续细化实现方案。
